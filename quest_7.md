## 2. Политика миграций

Мигратор `rhythm-db` использует Goose. SQL лежит в `database/migrations/`. В имени файла `YYYYMMDDHHMMSS_описание.sql` префикс в UTC задаёт номер и порядок миграции. В `tstamp` база записывает фактическое время применения.

Первая миграция создаёт базовую схему в пустой БД или регистрирует уже существующую схему после проверки её структуры и контрольной суммы. При переходе с предыдущей сборки команда `migrate` переводит подтверждённые номера `1` и `2` в идентификаторы с датой. Она меняет только `version_id` в `goose_db_version`. `tstamp` и пользовательские данные сохраняются. Вторая миграция добавляет индекс:

~~~sql
CREATE INDEX rhythm_diaries_updated_at ON rhythm_diaries (updated_at);
~~~

Goose выполняет создание индекса в транзакции. На большой таблице такой `CREATE INDEX` может блокировать записи. Перед выкладкой на заполненную рабочую БД оцениваем размер таблицы и допустимое окно для операции.

В Compose сервис `migrate` ждёт готовности PostgreSQL. Сервис `app` стартует после успешного завершения мигратора. На VPS ответственный за выкладку запускает `systemctl start rhythm-migrate.service`, затем проверяет результат и перезапускает приложение. Конкурирующие миграторы работают по очереди под блокировкой PostgreSQL. Перед изменением схемы второй участник сверяет SQL и результат на тестовой БД. [Compose](compose.yaml) · [Сервис миграций](deploy/native/rhythm-migrate.service).

Создать шаблон для следующего изменения можно командой:

~~~sh
make db-create NAME=add_example_index
~~~

Goose подставляет текущее UTC-время в имя нового файла с секцией `+goose Up`. Следующий файл нужно заполнить SQL, зарегистрировать в списке миграций и обновить контроль ожидаемой схемы в `backend/internal/postgresstore/migrations.go`. Уже применённый файл сохраняют побайтно. SQL и контрольную сумму можно посмотреть этими командами:

~~~sh
sed -n '1,220p' database/migrations/20261018090000_initial.sql
sed -n '1,160p' database/migrations/20261018090100_diaries_updated_at_index.sql
shasum -a 256 database/migrations/20261018090000_initial.sql
~~~

Для ручной проверки задайте `DATABASE_URL` для пустой тестовой БД через приватное окружение. Следующие команды сначала поднимут базовую схему, затем добавят данные проекта и применят индекс. В §4 эти шаги выполняет изолированный сценарий.

~~~sh
go run ./backend/cmd/db status
go run ./backend/cmd/db migrate-to 20261018090000
psql --no-psqlrc --set=ON_ERROR_STOP=1 --file=database/tests/quest_7_seed.sql "$DATABASE_URL"
go run ./backend/cmd/db migrate-to 20261018090100
go run ./backend/cmd/db status
go run ./backend/cmd/db migrate
~~~

В примере `psql` используйте локальный тестовый DSN без пароля в URL. Для подключения с паролем задайте `.pgpass`. Для обычного обновления настроенного окружения достаточно `make db-status` и `make db-migrate`.

В `goose_db_version` поле `id` идентифицирует строку, `version_id` — версию миграции, `is_applied` — факт применения, `tstamp` хранит время записи. В тесте после создания индекса появилась строка `id=3`, `version_id=20261018090100`, `is_applied=true`. Версия `0` — служебная, `20261018090000` — базовая схема. [Снимок таблицы из прогона](docs/evidence/quest-7-2026-11-14/result.json).

Посмотреть историю, контрольную сумму и индекс можно запросами:

~~~sql
SELECT id, version_id, is_applied, tstamp
FROM goose_db_version ORDER BY id;

SELECT version, checksum, applied_at
FROM rhythm_schema_migrations ORDER BY version;

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = current_schema()
  AND tablename = 'rhythm_diaries'
  AND indexname = 'rhythm_diaries_updated_at';
~~~

В `rhythm_schema_migrations` осталась версия `1` с SHA-256 исходного SQL `bf56b448909735999163e4596e7fb4e1bb082ce48ff2fd237a3c474226256059`.

**Ошибка и откат.** При ошибке CLI проверьте статус схемы и журнал. PostgreSQL откатывает незавершённую транзакцию. После устранения причины повторите миграцию. `migrate-to` поддерживает движение вперёд до указанной версии. После перевода идентификаторов используйте только сборку, которая понимает версии с датами. Предыдущая Goose-сборка ожидает записи `1` и `2` и отклонит новую историю. Перед обновлением сохраните проверенную копию. Восстановление из неё сначала проводят в отдельной БД и учитывают записи, сделанные с момента копирования.

## 3. Политика резервного копирования

Ежедневно в 03:15 по времени VPS таймер запускает полный `pg_dump` с задержкой до 15 минут. Перед изменением рабочей схемы делаем отдельную копию. Импортированные CSV и TCX становятся записями в дневнике, поэтому для них достаточно снимка БД. Конфигурацию сервиса и внешние ключи администратор хранит отдельно.

Копии в `/var/backups/rhythm` доступны оператору. Храним их семь суток и оставляем минимум две последние проверенные копии, даже если они старше срока. Очистка сначала показывает список кандидатов, затем с `--apply` проверяет его повторно. Для удаления нужна хотя бы одна свежая проверенная копия.

Наш RPO при штатном ежедневном копировании — **24 ч 20 мин**, целевой RTO — **60 минут**. Суточный снимок укладывается в выбранный для проекта предел потери записей. Оператор ежедневно смотрит журнал systemd, а раз в неделю и после изменений схемы или процедуры копирования проверяет восстановление в пустую БД. Подготовлен вариант зашифрованного хранения вне VPS на 30 суток. Подключение хранилища и внешних уведомлений остаётся за развёртыванием. [Политика резервного копирования v1.0 и обоснование целей](docs/database-backups.md#backup-policy).

Для ручного прогона укажите тестовую БД в `DATABASE_URL`. Создайте архив в новом приватном каталоге и проверьте его:

~~~sh
quest7_dir="$(mktemp -d /tmp/rhythm-quest7-manual.XXXXXX)"
quest7_stamp="$(date -u +%Y%m%dT%H%M%SZ)"
quest7_dump="$quest7_dir/rhythm-$quest7_stamp.dump"
python3 scripts/backup.py create "$quest7_dump"
python3 scripts/backup.py verify "$quest7_dump"
~~~

`verify` сверяет размер и SHA-256 со служебным файлом рядом с архивом, затем полностью читает архив через `pg_restore`. Следующая команда проверяет, можно ли восстановить данные в PostgreSQL.

Задайте `RHYTHM_RESTORE_DATABASE_URL` для подключения к тестовому кластеру с правом создания БД. В `assertions.sql` укажите проверки известных записей. Команда создаст пустую БД, восстановит архив, выполнит проверки и удалит созданную БД:

~~~sh
python3 scripts/backup.py restore-drill "$quest7_dump" \
  --test-database "rhythm_restore_test_$(date -u +%Y%m%d%H%M%S)_$$" \
  --assert-sql "$quest7_dir/assertions.sql"
~~~

`make quest-7-check` сам готовит SQL-проверки для двух записей из §4.

На каталоге с тестовыми копиями сначала запустите просмотр списка. Затем примените очистку и проверьте свежий архив:

~~~sh
python3 scripts/backup.py prune "$quest7_dir" --retention-days 7 --keep-last 2
python3 scripts/backup.py prune "$quest7_dir" --retention-days 7 --keep-last 2 --apply
python3 scripts/backup.py verify "$quest7_dump"
~~~

Для проверки удаления общий сценарий создаёт три настоящих архива и меняет время файлов у двух из них, чтобы смоделировать возраст 10 и 8 суток. Это позволяет увидеть кандидата на удаление сразу. [Команды и ограничения ручного восстановления](docs/database-backups.md#восстановление-в-отдельную-тестовую-бд).

Для повтора нужны Go 1.25, Python 3, PostgreSQL 16 и свободный локальный порт `55442`. На новом компьютере сначала скачайте Go-зависимости в кэш, который будет читать сценарий:

~~~sh
export GOMODCACHE="$(go env GOMODCACHE)"
go -C backend mod download
~~~

Сценарий запускает отдельный PostgreSQL на `127.0.0.1:55442`, создаёт тестовые базы и останавливает кластер после проверки. Он удаляет временные архивы и печатает путь к `result.json`. Если порт занят, задайте другой через `QUEST_ARGS`:

~~~sh
make quest-7-check QUEST_ARGS='--pg-port 55443 --evidence-dir /tmp/rhythm-quest7-second-run'
~~~
