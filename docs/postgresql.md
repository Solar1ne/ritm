# PostgreSQL: запуск, перенос и восстановление

На этом компьютере сайт переведён на PostgreSQL 16. Локальная БД: порт 55432, только 127.0.0.1. Отдельная приватная конфигурация находится в `.local/database.env` (0600), кластер — `.local/postgres`. `.local` исключён и из Git, и из Docker build context. Пароли и SQL dump не публикуются в evidence.

## Обычный локальный запуск

Из корня проекта посмотрите текущую версию схемы. Перед обновлением существующей БД создайте и проверьте копию по инструкции ниже.

```sh
make db-status
make db-migrate
python3 scripts/dev.py start
```

Скрипт использует существующий приватный DATABASE_URL, при необходимости запускает только кластер этого проекта и поднимает сайт на 127.0.0.1:8080. Для остановки сайта — Ctrl+C. PostgreSQL продолжает работать. Остановить именно локальный кластер можно установленным `pg_ctl -D "$PWD/.local/postgres" -m fast -w stop` (на этой машине бинарники в `/opt/homebrew/opt/postgresql@16/bin`). Не останавливайте БД, пока сайт принимает записи.

В новом окружении сначала создайте PostgreSQL database и роль без superuser; передайте DATABASE_URL через secret/environment. Для remote обязателен `sslmode=verify-full` и доверенный CA. Затем:

```sh
go run ./backend/cmd/db migrate
go run ./backend/cmd/server
```

`/api/health` возвращает `storage: "postgresql"`. Ошибка подключения/схемы останавливает запуск; автоматического перехода на JSON нет. Без DATABASE_URL чистая немигрированная DATA_DIR всё ещё поддерживается как ограниченный однопроцессный режим. После cutover старую директорию нельзя использовать для продолжения истории.

Goose использует номер версии из UTC-префикса имени файла. Если `db-status` показывает `needsVersionNormalization`, `db-migrate` переведёт подтверждённые записи `1` и `2` в версии с датами. Индекс и базовая схема, уже присутствующие в БД, повторно не применяются. Время применения сохраняется в `goose_db_version.tstamp`. Сборка со старой нумерацией ожидает прежние номера и после перевода истории потребует отдельного плана отката. [Политика миграций](../quest_7.md#2-политика-миграций).

## Docker Compose для нового размещения

Заполните `.env` по `.env.example`: домен и два разных пароля PostgreSQL (административный и прикладной). `docker compose up --build -d` запускает БД → отдельную миграцию → приложение → Caddy. DB порт наружу не публикуется. Прикладная роль создаётся `deploy/postgres-init.sh` только в пустом volume и не имеет superuser/createdb/createrole.

Это конфигурация нового размещения. Если старый Compose уже содержит JSON-данные, сначала выполните офлайн-перенос; запуск новой БД не импортирует старый volume сам. Нельзя удалить volume ради смены пароля; для существующей БД пароль меняется административно и синхронно с secret приложения.

В текущей среде `docker compose config --quiet` проверен; Docker daemon не запущен, поэтому запуск контейнеров не заявляется. Настоящая работа PostgreSQL, миграция и backup/restore проверены в нативном локальном контуре.

## Перенос существующего JSON-хранилища

1. Остановите все старые процессы сайта. Бинарники до этой версии не умеют учитывать migration lock.
2. Скопируйте весь DATA_DIR, включая `.accounts.json`/`.session-secret`. Сохраните действующий внешний SESSION_SECRET, если он использовался. Копия должна быть приватной; не кладите её в Git.
3. Поднимите пустую тестовую БД, примените схему, импортируйте отдельную копию файлов и проверьте результат/сессии. Не запускайте сайт на пустой целевой БД до импорта — startup создаст ключ, и цель перестанет быть пустой.
4. Для основной пустой БД выполните:

```sh
go run ./backend/cmd/db migrate
go run ./backend/cmd/db import-json -dir /absolute/path/to/data
```

5. Запустите сайт с DATABASE_URL и проверьте прежнюю сессию. Сохраните исходный snapshot и SQL backup.

Import проверяет размер/структуру/принадлежность, исключает файловые I/O, записывает `.postgres-cutover.json` со статусом pending до SQL COMMIT и перечитывает сохранённые данные в транзакции. После успешного COMMIT marker становится completed. Если процесс прерван, оставьте marker и повторите ту же команду с неизменной source: одинаковый fingerprint безопасен. Не удаляйте marker и не продолжайте в старых файлах — это создаст две разные истории. SQL timestamp имеет микросекундную точность; credential bytes, версии, ID, receipts и исходный ключ сохраняются.

При неудачной миграции после pending устраните SQL-причину и повторите тот же snapshot. Возврат к файловому snapshot — отдельная ручная процедура с остановкой SQL-сайта; после новых SQL-записей он приведёт к потере этих записей и не является штатным rollback.

## Резервирование

Команды создания, проверки, отдельного восстановления и очистки описаны в [руководстве по резервному копированию](database-backups.md). Схема и история Goose входят в SQL-копию. Сценарий `make quest-7-check` воспроизводит проверку на синтетических данных.

Октябрьские файлы переноса и архивы сохранены в `.local/backups/`. Их проверка описана в [отчёте о переносе](evidence/postgresql/cutover.json). Эти архивы были созданы предыдущим инструментом, поэтому у них нет manifest-файлов нового формата.

## Проверки

```sh
go -C backend test ./...
go -C backend vet ./...
staticcheck ./backend/...
# Для реальных SQL/race-тестов задайте отдельный DSN, имя БД заканчивается на _test:
RHYTHM_TEST_DATABASE_URL='postgres://…/rhythm_test?sslmode=disable' go -C backend test -race ./...
npm test
npm run check
```

Без RHYTHM_TEST_DATABASE_URL PostgreSQL integration-тесты явно SKIP. Каждый SQL-тест создаёт и удаляет только собственную случайную схему в тестовой БД. Для браузерных сценариев используйте отдельный сайт на 18081, направленный в тестовую БД. `scripts/first-run-check.mjs` и существующие acceptance scripts создают только синтетические истории. [Подробности реализации и ограничений](adr/008-postgresql-storage.md).
