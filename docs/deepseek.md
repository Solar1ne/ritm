# Подключение DeepSeek

17.10.2026. В Ритме добавлен отдельный серверный адаптер DeepSeek. Последний полный браузерный прогон получил **3 из 3 реальных ответов**: вопрос о плане, разбор наблюдений за 14 дней и черновик отметки из свободной фразы. Это вызовы внешней модели, без подмены ответов fixtures. Использован только искусственный профиль в отдельной PostgreSQL `rhythm_test`; после проверки его данные удалены.

Основной сайт на [127.0.0.1:8080](http://127.0.0.1:8080/#assistant) перезапущен с DeepSeek и PostgreSQL; [проверка статуса](evidence/deepseek/runtime.json) подтверждает включённые аккаунты и провайдера.

## Реализация

`internal/deepseek` следует существующему адаптеру `internal/openai`: stdlib HTTP, один запрос, ограниченный ответ, отмена через context, запрет переходов по redirect, отсутствие повторов. Новых зависимостей нет. Независимый контракт, инструкция, JSON-схема и строгий разбор результата находятся в `internal/aicoach`; модель не изменяет план и не пишет в БД.

Согласно [официальному первому запросу](https://api-docs.deepseek.com/), используются `https://api.deepseek.com/chat/completions` и `deepseek-flash`. Включён [JSON output](https://api-docs.deepseek.com/guides/json_mode/), thinking явно отключён, ответ ограничен 2200 токенами. JSON mode не заменяет локальную проверку полей, ссылок на факты, дат, статусов и диапазонов измерений.

Composition root выбирает `AI_PROVIDER=deepseek|openai`. Без явного выбора используется единственный настроенный ключ; наличие обоих ключей требует выбора. Ключ одного сервиса никогда не используется для другого. Неуспешный ответ не выдаётся за ответ локальных правил.

Экран согласия на каждый запрос показывает получателя и его условия. Подписанный токен связывает просмотренный контекст с аккаунтом, задачей, revision, сроком, **провайдером и моделью**. После их смены старое согласие отклоняется. Ключ, имя профиля, аккаунт и Telegram ID не входят в автоматически собранный контекст; свободный текст показывается перед отправкой. Ответы AI не сохраняются в истории приложения; отсутствие хранения у DeepSeek не обещается. Ссылка на [политику DeepSeek](https://cdn.deepseek.com/policies/en-US/deepseek-privacy-policy.html) дана в интерфейсе, а не заменена условиями OpenAI.

## Проверки и ограничения

- [Живой браузерный прогон](evidence/deepseek/live-verified/results.json): три вызова, проверка получателя согласия, отсутствие автоматических записей, правка сна с 7,5 до 8 часов и отдельное сохранение в PostgreSQL с перезагрузкой. Ширины 320/390/768/1440 px, ошибок JavaScript нет.
- В последнем прогоне ответы заняли 10,122 с для checkin, 2,584 с для review, 2,139 с для ask. Это три наблюдения, не SLA и не статистическая оценка качества.
- Первый прогон остановился на одном HTTP503 при review после успешного checkin. Первичная причина не установлена; тело внешней ошибки не сохранялось. [Первичный результат](evidence/deepseek/live/failure.json) оставлен в доказательствах. Отдельный диагностический review и последующий полный прогон успешны. Это не обещание бесперебойности внешнего сервиса.
- [Автоматические проверки](evidence/deepseek/checks.json): `go test -race ./...`, `go vet ./...`, `staticcheck ./...`, 60 JavaScript-тестов и проверка синтаксиса, три теста приватной native-конфигурации. SQL integration-тестам требуется отдельный DSN; реальный PostgreSQL в этом изменении проверен браузерным сценарием.
- Go-тесты покрывают выбор провайдера без ошибочного fallback, таймауты, невалидный JSON, лишние/пропущенные поля, выдуманные ссылки и даты, ошибки401/402/429, redirect, отмену без платного запроса, освобождение квот, устаревшее согласие после смены провайдера/модели, отсутствие утечки секретов из транспортных ошибок.

На один вызов отведено 20 секунд для DeepSeek, 3 секунды для OpenAI. `AI_TIMEOUT_SECONDS` допускает 1–30 секунд; сервер и браузер ожидают дольше этого предела. Сохраняются четыре параллельных вызова, шесть на аккаунт за десять минут, 60 попыток на процесс в час по умолчанию и circuit breaker. Ошибки не изменяют дневник. В журнал попадают только провайдер, задача, длительность, категория ошибки и HTTP-статус; текст запроса/ответа и ключ туда не попадают.

Значимые риски: нестабильность и стоимость внешнего API, ошибки смысла даже при корректном JSON, обработка согласованных данных внешним провайдером. Транзакции/миграции БД — N/A: схема и существующий путь подтверждённой записи не менялись. Новые фоновые goroutine, очереди и SDK — N/A: запрос принадлежит жизненному циклу HTTP. Полный пользовательский пилот, медицинская проверка правил, публичный HTTPS и вход через настоящего Telegram-бота этим smoke не заменяются.

## Настройка и повторная проверка

Для native-запуска сохраните `AI_PROVIDER=deepseek`, `DEEPSEEK_MODEL=deepseek-flash` и `DEEPSEEK_API_KEY` в `.local/integrations.env` с правами0600. `python3 scripts/dev.py start` читает этот файл вместе с `.local/database.env`, без shell-исполнения; переменные окружения имеют приоритет. `.local` исключён из Git и Docker build context. Для Compose задайте те же переменные в серверном `.env` согласно `.env.example`.

Ключ, отправленный в переписку, следует перевыпустить в [кабинете DeepSeek](https://platform.deepseek.com/api_keys), заменить в приватной конфигурации и перезапустить процесс. Новый ключ не требуется отправлять в чат.

Повторный платный smoke выполняется только при явном флаге и требует отдельного QA-сервера на18081 с `rhythm_test`. Он создаёт собственную браузерную сессию и искусственный профиль, делает максимум три AI-запроса и удаляет только этот профиль:

```sh
RHYTHM_LIVE_AI=1 PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs node scripts/deepseek-live-check.mjs
GOCACHE=/tmp/rhythm-go-cache GOMODCACHE=/tmp/rhythm-go-modcache go test -race ./...
GOCACHE=/tmp/rhythm-go-cache GOMODCACHE=/tmp/rhythm-go-modcache go vet ./...
GOCACHE=/tmp/rhythm-go-cache GOMODCACHE=/tmp/rhythm-go-modcache STATICCHECK_CACHE=/tmp/rhythm-staticcheck-cache staticcheck ./...
npm test
npm run check
python3 scripts/test_dev.py
```

Работа выполнена по ECC api-connector-builder. Git-коммиты не создавались.
