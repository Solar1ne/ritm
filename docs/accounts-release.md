# Ритм: постоянный аккаунт и улучшения входа

17 октября 2026. [Открыть сайт](http://127.0.0.1:8080/). В верхней панели нажмите **«Войти» → «Создать аккаунт»**. Уже сохранённый гостевой дневник присоединяется при регистрации после вашего подтверждения.

## Что изменилось

- Регистрация и вход по логину и паролю; история доступна в другом браузере и после перезапуска сервера.
- Восстановление по однократному резервному коду, скачивание кода и выпуск нового с подтверждением пароля.
- Смена пароля, список активных сеансов, завершение остальных сеансов и настоящий серверный выход.
- Текущий дневник сохраняется при регистрации; прежняя гостевая cookie перестаёт открывать его. Вход в другой аккаунт не объединяет истории автоматически.
- Формы используют тот же премиальный стиль, подписанные поля и управление показом пароля; проверены на 320, 390 и 1440 px. Питание заново загружается после смены аккаунта без переключения экрана.

Почта не запрашивается: письма, подтверждение email и почтовое восстановление не реализованы. Сохраните резервный код при регистрации. Если потеряны и пароль, и код, автоматического восстановления нет. «Удалить данные» очищает дневник, но сохраняет учётную запись.

## Проверка и доказательства

Финальная сборка прошла `go test -race`, `go vet`, `staticcheck`, проверку gofmt, сборку, синтаксическую проверку JS и **57 JavaScript-тестов**. В реальном Chrome прошли **65 браузерных проверок**: 12 новых сценариев аккаунта и 53 прежних сценария. Страничных JavaScript-ошибок нет. Машинные результаты: [verification.json](evidence/accounts/verification.json), [цикл аккаунта](evidence/accounts/browser.json), [прежние сценарии](evidence/accounts/browser-regression.json), [общий итог](evidence/accounts/checks.json).

Свежий [RAT](evidence/accounts/rat.json): 16/16 случаев, 5/5 критических, 5000 вызовов без ошибок; p95 правил 0,005917 мс. [HTTP smoke](evidence/accounts/http-load.json): 300/300 успешных записей, 30 секунд при target 10 RPS, p95 запроса 11,666083 мс, ошибок/setup/cleanup failures нет. Это локальный Go + JSON, не SQL, не массовый вход с KDF и не мобильная сеть. Покрытие в `coverage.out` рассчитано стандартно по пакетам: интеграционные тесты HTTP исполняют сервис аккаунтов, но этот процент отдельно не переносится в строку пакета accounts.

На пользовательском localhost:8080 запущен тот же проверенный бинарник. [Проверка перезапуска](evidence/accounts/restart.json) подтверждает совпадение frontend с исходниками, доступность аккаунтов, сохранение всех 89 прежних файлов и неизменность ключа сессии. Перед обновлением создана приватная копия каталога. Отчёты предыдущих этапов остаются историческими, результаты этой версии лежат в `evidence/accounts/`.

```sh
GOCACHE=/tmp/rhythm-go-cache go test -race ./...
GOCACHE=/tmp/rhythm-go-cache go vet ./...
GOCACHE=/tmp/rhythm-go-cache STATICCHECK_CACHE=/tmp/rhythm-staticcheck-cache staticcheck ./...
npm run check
npm test
```

Браузерные проверки аккаунта запускаются только на отдельном локальном сервере, чтобы не создавать тестовые аккаунты в пользовательском каталоге:

```sh
DATA_DIR=/tmp/rhythm-accounts-qa ADDR=127.0.0.1:18081 go run ./cmd/server
# В другом терминале, с установленными Chrome и Playwright:
PLAYWRIGHT_MODULE=/absolute/path/to/node_modules/playwright node scripts/accounts-check.mjs
go run ./cmd/rat -json
go run ./cmd/loadtest -url http://127.0.0.1:18081 -rps 10 -duration 30s
```

Auth-тесты проверяют конкурирующие регистрации и recovery, старые cookies и коды, два браузера, повторный вход, смену секрета, отказ хранилища и отменённый запрос. HTTP smoke с четырьмя workers измеряет основной путь дневника. AI и Telegram в браузерных тестах используют явно обозначенные fixtures; живой провайдер и настоящий бот ими не подтверждены.

## Почему так и какие риски остаются

Аккаунт — отдельный Go-сервис; файловый адаптер атомарно меняет владельца существующего дневника без копирования истории. Стандартный KDF, случайные токены, хеширование сохранённых секретов, отзыв, проверка Origin/binding и ограничение попыток уменьшают риск захвата аккаунта. Одновременная запись и регистрация проверяют одного владельца под storage lock. Подробнее: [ADR-07](adr/007-persistent-website-accounts.md) и [API](api.md).

Хранилище работает в одном процессе. Backup должен включать **весь DATA_DIR со скрытыми файлами** и серверный секрет; отдельно удалять/восстанавливать `.accounts.json` нельзя. После появления аккаунтов старый бинарник, не проверяющий их владельца, непригоден для rollback. [Правила сохранения и возврата версии](adr/007-persistent-website-accounts.md#совместимость-backup-и-возврат-версии).

Полный публичный продукт ещё не готов: нужны HTTPS-размещение и реальный Telegram-бот, серверный OpenAI-ключ и live smoke, внешняя проверка удобства/гипотез из презентации. Нет прямого API часов, фоновых Telegram-напоминаний, MFA или почтового входа. Код этих отсутствующих возможностей не подменяется визуальными заглушками. [Полная сверка с презентацией](presentation-readiness-audit.md).
