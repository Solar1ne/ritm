## Формулировка RAT до проверки

**Считаем:** при валидном профиле и дневнике система формирует недельный план и отдельное объяснимое предложение; при конфликте успешного выполнения с недосыпом/усталостью восстановление важнее прогресса. Повтор записи или вычисления не создаёт искусственный прогресс.

**Проверяем так:** запускаем table-driven сценарии Go domain и исполняемую команду RAT. В набор входят усталость, недосып, два разных пропуска, полное выполнение, конфликтующие признаки, пустая история, границы и повторные данные. Отдельно измеряем 5 000 локальных вычислений. Затем проводим реальный HTTP load с сохранением данных через API текущего adapter.

**Успех зафиксирован до нового прогона:** 5/5 критических защитных развилок; ≥90% всех заявленных сценариев; локальный p95 rule engine <50 мс на 5 000 вычислений. Для HTTP: 10 RPS, не ниже расчётных 8.33 RPS; p95≤450 мс; 0 неожиданных серверных/транспортных ошибок. Локальный прогон 30 секунд — smoke, не доказательство долговременной работы.

**Получилось в новом Go-прогоне 17.10.2026:** [16/16 сценариев, 5/5 критических, 5 000 вызовов без ошибок, local p95 0.007375 мс](evidence/full-product/rat.json). Критерии выполнены на искусственных данных. Финальный [HTTP smoke](evidence/full-product/http-load.json) подтвердил 300/300 записей за 30 секунд, 9.99975 RPS, p95 запроса 12.10075 мс, 0 ошибок и drops. Он шёл на фоне локальных браузерных проверок и не измеряет изолированную ёмкость оборудования. Число ~0.007 мс из презентации относится к описанному командой старому Node.js PoC и здесь не используется как новый результат.

Фиксированный набор новой реализации находится в [internal/rat/cases.go](../internal/rat/cases.go); его использует [TestRATFixedScenarios](../internal/rhythm/rhythm_test.go). Базовый профиль — 3×45=135 минут. Пять последних сценариев помечены критическими до запуска.

## Воспроизведение

Из корня репозитория:

```sh
go version
go test ./...
go vet ./...
go test -race ./...
staticcheck ./...
go run ./cmd/rat
```

В отдельном терминале:

```sh
DATA_DIR=/tmp/rhythm-defense-data go run ./cmd/server
```

Открыть `http://127.0.0.1:8080`, выполнить браузерный сценарий, затем запустить:

```sh
go run ./cmd/loadtest -url http://127.0.0.1:8080 -rps 10 -duration 30s -output docs/evidence/full-product/http-load.json
```

Команда запуска использует отдельную локальную data-директорию, чтобы нагрузочные данные не смешивались с пилотом. Для повторяемого набора использовать заранее выбранный чистый каталог; не удалять чужую data-директорию. По умолчанию сервер слушает `127.0.0.1:8080`, часовой пояс — `Europe/Moscow`; параметры `ADDR`, `DATA_DIR`, `TIME_ZONE`, `PUBLIC_URL`, `SESSION_SECRET` описываются в README сборки. При сравнении прогонов указывать одинаковые условия. Для следующего шага увеличить окно до `-duration 5m`, проверить achieved RPS, число ошибок и размер файлов; для PostgreSQL повторить после внедрения adapter.

`cmd/loadtest` по умолчанию принимает только loopback; внешний адрес требует явного `-allow-remote`. Допустимы RPS 1–1000, длительность 1 с–10 мин, workers 1–32. У каждого worker отдельный cookie jar и sessionBinding; подготовка/cleanup не входят в измерение. Открытый планировщик считает пропущенные задания ошибками, а каждый HTTP200 проверяется по revision, записанному факту, recover и 72 минутам. Неуспешные критерии дают ненулевой exit code и сохраняемый failed report. Клиент не печатает cookie, binding или данные авторизации.

Если sandbox блокирует системные кэши, для staticcheck можно явно выбрать доступные каталоги:

```sh
GOCACHE=/tmp/rhythm-go-cache STATICCHECK_CACHE=/tmp/rhythm-staticcheck-cache staticcheck ./...
```

Предупреждение `matched no packages` не считается успешным анализом: в этой среде оно могло скрывать отказ доступа к cache.

## Короткая демонстрация работающего образца

Защита по критериям длится 15 минут и проходит как разговор по заранее загруженным материалам. Не стоит тратить её на линейный пересказ 32 слайдов. Открыть приложение и держать рядом одну страницу evidence; распределить ответственных за продукт, правила, архитектуру и эксперимент.

1. **0:00–1:00, продукт.** Показать реальную задачу новичка: три дня, базовое занятие 45 минут, цель «тонус». На экране получается 135 минут в неделю. Уточнить, что это демонстрационная программа и ещё не экспертное назначение.
2. **1:00–3:00, основной сценарий.** Открыть день, внести факт и сон/усталость; после перезагрузки данные сохраняются. Показать текущую неделю отдельно от предложения и причины. Не вводить факт будущей даты как реальное выполнение.
3. **3:00–5:00, рискованный конфликт.** В области синтетических сценариев показать усталость 9/10, сон 5 ч и хорошее выполнение. Из 3×45=135 получается предложение 2×36=72. Показать recovery как приоритет; синтетический пример не записывается в дневник.
4. **5:00–6:00, альтернативные ветки.** Два разных пропуска дают упрощение. Полное выполнение и восстановление дают отдельное предложение 45→47 минут; повторный расчёт не превращает 47 в 49. Для неполных данных прогресс не обещается.
5. **6:00–8:00, эксперимент.** Запустить `go run ./cmd/rat`, показать фактические pass/fail и local p95. Затем открыть отчёт HTTP load: target/achieved RPS, count, p95 и errors. Объяснить, что local rule latency и HTTP latency — разные измерения.
6. **8:00–10:00, архитектура.** По текущему C4 провести запрос Web→Go→JSON→Go→Web. Показать ADR rule engine против LLM-only и ограничения одного процесса. Отдельно открыть целевой PostgreSQL C4.

## Готовые честные ответы на вопросы

**«Почему не FastAPI из презентации?»** Исходного backend не было. Команда выбрала Go под текущий стандарт разработки; бизнес-сценарий и границы сохранены. Это решение о сопровождении и запуске, не неподтверждённый тезис о скорости Python.

**«Где здесь ИИ?»** В текущем обязательном сценарии LLM нет. План рассчитывает rule engine. Вопросы о плане, прогрессе и восстановлении обрабатывает детерминированный помощник с указанием фактов дневника. Это сознательный обход риска; возможный разговорный слой потребует отдельного исследования.

**«Вы доказали безопасность рекомендаций?»** Нет. Мы проверили технические инварианты и конфликты на искусственных данных. Пороги демонстрационные; план экспертизы указан отдельно.

**«8.33 RPS — это измеренная аудитория?»** Нет. Это расчёт из пяти явно указанных гипотез. HTTP load измеряет конкретный сервер с заданной частотой; размер пользовательской базы этим не измеряется.

**«450 мс уже доказаны?»** В таблице пути это проектная сумма бюджетов. Фактические p95 берутся только из отчёта. Даже успешный HTTP loopback не включает browser render, мобильную сеть и production TLS.

**«Почему JSON, если на слайде PostgreSQL?»** Проверяем сквозное серверное сохранение в одном процессе без дополнительного DB-server. Concurrent/restart tests проверяют текущий контракт; PostgreSQL показан отдельно как следующая архитектура и ещё не измерен.

**«Как доказано, что пользователи вернутся?»** Пока не доказано. Есть критерии UX-теста и двухнедельного пилота, определён знаменатель и сроки. Числа 60% и 70% — пороги будущих проверок, не результаты.
