# Ритм на VPS — 17 октября 2026

Новая схема Goose, структура исходников и проверка резервирования описаны в [квесте 7](../quest_7.md). Ниже зафиксировано размещение октября. Обновление VPS этой сборкой пока не подтверждено.

Рабочий адрес: **https://176.119.147.97/**. Сервер `purple-ubuntu2404-spb-01`, Ubuntu 24.04, amd64, 1 vCPU, 961 MiB RAM. Релиз: `20261017T121911Z`.

## Что запущено

| Компонент | Размещение |
|---|---|
| Go-приложение с встроенными JS/CSS/fonts | `/opt/rhythm/current/rhythm`, `rhythm.service`, пользователь `rhythm` |
| PostgreSQL 16 | `postgresql@16-main.service`, БД и роль `rhythm` |
| Nginx | Публичные порты 80 и 443; HTTP перенаправляется на HTTPS |
| DeepSeek | Ключ только в `/etc/rhythm/app.env`, root:root, 0600 |
| HTTPS | Let’s Encrypt, IP SAN `176.119.147.97`, профиль `shortlived` |
| Продление сертификата | `rhythm-certbot.timer`, дважды в сутки с разбросом до 30 минут |
| Резервные копии | `rhythm-backup.timer`, ежедневно в 03:15–03:30 MSK, `/var/backups/rhythm`, 0700; файлы 0600 |

На сервер загружены только Linux-бинарники и конфигурации из `deploy/native`. Исходники, локальная БД, пользовательские дневники, тестовый демопрофиль с компьютера и материалы презентации не загружались. У сервера новая БД. Проверочный аккаунт удалён после тестирования. Дамп, использованный для проверки восстановления, содержит только синтетический проверочный аккаунт; он удалится обычной политикой хранения.

Для VPS с 1 ГБ памяти выбран нативный systemd-деплой. Go собирается на компьютере под `linux/amd64`; на сервере не нужны Go, Node.js или Docker. Лимиты приложения: `GOMEMLIMIT=128MiB`, `MemoryHigh=192M`, `MemoryMax=256M`, `GOMAXPROCS=1`. Добавлен 1 GiB swap, PostgreSQL настроен на 40 соединений и 128 MB shared buffers. Это конфигурация для PoC и небольшой нагрузки; нагрузка в 10 000 пользователей здесь не проверена.

## Границы доступа и изменения кода

- Приложение слушает только `127.0.0.1:8080`, PostgreSQL — loopback и Unix socket. Firewall разрешает только 22, 80, 443. SSH-доступ пользователя сохранён.
- Приложение и миграции подключаются к PostgreSQL через Unix socket с peer-аутентификацией системного пользователя `rhythm`. Роль не имеет SUPERUSER, CREATEDB или CREATEROLE. Отдельный пароль БД не требуется.
- `PUBLIC_URL=https://176.119.147.97`, поэтому cookies имеют Secure/HttpOnly; проверка Origin и привязка запросов к текущей сессии остаются включены.
- Новый `TRUSTED_PROXY_CIDRS=127.0.0.1/32` разрешает принимать один валидный `X-Real-IP` только от локального Nginx. Nginx всегда перезаписывает заголовок реальным адресом TCP-клиента. Клиентские `X-Forwarded-For`, списки IP, дублированные заголовки и незнакомые прокси не получают доверия. Не задавайте `0.0.0.0/0` и не открывайте 8080 наружу.
- Квоты входа теперь разделяются по реальному клиенту, а не по общему адресу прокси. Дополнительно Nginx ограничивает частоту API, входа и число соединений. Это не полноценная защита от распределённого DDoS.
- `GET /api/state` читает пустое состояние без создания строк в БД. Первая запись создаёт дневник в транзакции; обновление недель существующего профиля сохраняет прежний атомарный механизм. Это устраняет рост пустых дневников от простого просмотра страниц, но не заменяет общие квоты хранения для пользователей, которые действительно пишут данные.
- AI остаётся необязательным адаптером: до 60 запросов/час на процесс, отдельные квоты пользователя и конкурентности; провайдер не изменяет дневник автоматически.

Дополнительные слои, новые Go-зависимости, фоновые goroutine и изменения HTTP JSON-контрактов не понадобились. Новые транзакции не вводились; миграция схемы осталась прежней. Перезапуск контролирует systemd, время корректно синхронизируется с NTP.

## Обслуживание

Подключение: `ssh root@176.119.147.97`. Пароль в документации не хранится.

```sh
systemctl status rhythm nginx postgresql@16-main --no-pager
curl --fail https://176.119.147.97/api/health
journalctl -u rhythm --since '1 hour ago' --no-pager
systemctl list-timers rhythm-certbot.timer rhythm-backup.timer
systemctl restart rhythm
systemctl start rhythm-backup
```

Логи Nginx: `/var/log/nginx/rhythm-access.log` (метод, URI без query, статус, время ответа) и `rhythm-error.log`. Стандартный Ubuntu logrotate обслуживает `*.log`. Полные запросы, пароли и ответы AI в access log не записываются. Журналы systemd доступны через `journalctl`.

### Сертификат

Первый сертификат действует до 24 октября 2026; короткий срок является особенностью IP-сертификата. Продление автоматическое, без остановки сайта: ACME challenge обслуживается Nginx из `/var/lib/rhythm-acme`, после успешного продления выполняются `nginx -t` и reload.

```sh
/opt/certbot/bin/certbot certificates
systemctl status rhythm-certbot.timer --no-pager
journalctl -u rhythm-certbot --since '7 days ago' --no-pager
/opt/certbot/bin/certbot renew --dry-run --run-deploy-hooks \
  --deploy-hook '/usr/sbin/nginx -t && /usr/bin/systemctl reload nginx'
```

Установлен Certbot 5.4.0 в `/opt/certbot`. Обновления этой venv не устанавливаются автоматически; периодически обновляйте Certbot и проверяйте `renew --dry-run`. Поддержка IP и требования к профилю проверены по [официальной инструкции Let’s Encrypt](https://letsencrypt.org/2026/03/11/shorter-certs-certbot); установка venv соответствует [инструкции Certbot](https://certbot.eff.org/instructions?os=pip&ws=nginx).

### Резервные копии и восстановление

Сохраняются завершённые custom-format pg_dump; незавершённый файл удаляется при ошибке. Файлы старше семи полных суток удаляются при успешном следующем backup. Дампы содержат частные данные и ключ сессий: не публиковать и не помещать в webroot.

Для проверки восстановления создайте отдельную временную БД через `runuser -u postgres -- createdb <уникальное_имя>`, восстановите конкретный файл командой `pg_restore --exit-on-error --no-owner --no-acl --dbname=<имя> <файл>`, проверьте данные и удалите только эту тестовую БД. Восстановление поверх рабочей БД требует отдельного плана, остановки записей и сохранения текущего состояния.

Копии сейчас находятся на том же VPS. Они помогают восстановиться после ошибки приложения, но не защищают от потери всего сервера. Внешнее хранилище и независимые уведомления об отказах ещё не настроены.

### Обновление и откат

1. Прогнать проверки. Собрать `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags='-s -w'` отдельно для `./backend/cmd/server` и `./backend/cmd/db`. Создать новый каталог `/opt/rhythm/releases/<timestamp>` с бинарниками, конфигурациями и `SHA256SUMS`. Не копировать `.local`, `.env`, `.data` или всю рабочую папку.
2. Перед обновлением запустить `rhythm-backup`. Сохранить текущий путь в `/opt/rhythm/previous`. Проверить совместимость новой схемы со старым бинарником.
3. Атомарно переключить `/opt/rhythm/current` через новый symlink и `mv -Tf`. Запустить `systemctl start rhythm-migrate`, затем `systemctl restart rhythm`. Миграции выполняются явно, не при каждом аварийном перезапуске.
4. Проверить health, вход и сохранение данных. Для отката переключить symlink на проверенный предыдущий релиз и перезапустить приложение. У первого релиза предыдущей версии нет. Деструктивного отката схемы не предусмотрено.
