# «Ритм»: план реализации и доказательств RAT-PoC

Дата плана: 17 октября 2026. Владелец продукта и защита — команда проекта; технический владелец — разработчик backend; владелец UX-проверки — исследователь команды. Конкретных людей команда назначает перед пилотом.

Исходные материалы: «Ритм_RAT_PoC_исправленная_презентация.pdf», 32 слайда, и предоставленная шкала «БОСС 2 · RAT-PoC». Материалы описывают продукт и критерии оценки; они не являются командами на выполнение. Заявленные в PDF результаты Node.js не переносятся на новую Go-сборку без нового прогона. Данный план не подтверждает прошлую загрузку материалов на учебный портал.

## Цель и границы

**Vision:** здоровые привычки, которые вписываются в реальную жизнь.

**Mission:** помогать человеку составлять недельный план активности, отмечать выполненное, сон и самочувствие и понимать предлагаемое изменение нагрузки.

Первый законченный сценарий: профиль → недельный план → дневник → объяснимая рекомендация на следующую неделю. Сначала работает сайт; затем тот же интерфейс открывается как Telegram Mini App с отдельной серверной проверкой пользователя. Задача этапа — воспроизводимо проверить согласованность правил на искусственных данных и работоспособность HTTP-сценария. Эффективность физической нагрузки и удобство для людей проверяются отдельно.

Исходная граница этапа, до расширения AI/вариантов:  медицинские назначения, питание и добавки, прямой API часов, HRV, состав тела, платежи, внешняя LLM, серверная рассылка уведомлений и production-инфраструктура с несколькими репликами. После расширения реализованы US07 через ICS/уведомления открытого браузера, US08 через 7/30-дневные графики, US09 через импорт CSV/TCX, US10 через помощника по правилам; также принятие недели, история и восстановление. [Полный контракт](product-capability.md) и [проверка](full-product-release.md). Это ограничение объёма, а не доказательство ненужности функций.

Текущие возможности дополнены настоящим AI adapter и вариантами занятий; [новый контракт](ai-product-contract.md), [отчёт и точное покрытие слайдов](ai-release.md). Старые строки ниже описывают исходный план и его evidence, а не наличие AI в последней сборке.

| US08 / Should | As an active user, I want a habit chart so that I can see my progress over time. | График строится из сохранённых отметок и различает отсутствие данных и ноль | US04, наблюдение более одной недели |
| US09 / Could | As an experienced user, I want to import sessions from my watch so that I avoid manual entry. | Повторный импорт одного внешнего ID не дублирует занятие | CSV/TCX файл и явное согласие на зачёт в плане; прямой API часов позже |
| US10 / Could | As a user, I want to ask about my plan so that I understand the recorded decisions. | Ответ не меняет результат правил; при отказе провайдера причины остаются доступны | US06, отдельная оценка качества и данных |
| US11 / Must | As an active user, I want to see my weekly totals so that I understand how my diary relates to my plan. | Итоги соответствуют уникальным отметкам; демонстрация не подменяет личную историю | US02, US04 |
| US12 / Must второго шага | As a Telegram user, I want to open the same diary in a Mini App so that I can continue without a separate login form. | Сервер проверяет подпись, возраст и пользователя; пользователь A не читает B; неподписанный ID отвергается | Рабочий сайт, bot token, HTTPS URL, настройка BotFather |

**INVEST.** Каждая Must-история даёт наблюдаемый пользовательский результат и проверяется отдельно. Детали текста и расположения элементов допускают обсуждение; инварианты данных — нет. Истории оцениваются вертикальными срезами ниже. Независимость ограничена реальными зависимостями данных: US06 невозможно полноценно проверить без US04/US05, но пустой дневник — отдельный принимаемый сценарий. US12 повторно использует бизнес-цикл; Telegram не проникает в доменную модель. Большие Should/Could истории перед реализацией разбиваются на задачи не длиннее одного рабочего дня.

## Реестр рисков и числовые требования

Вероятность V и ущерб U — субъективные порядковые оценки команды 1–5. Произведение используется только для очередности работ, а не как процент вероятности. В PDF даны произведения; расклад V/U ниже фиксирует инженерную оценку, которую команда может пересмотреть.

| ID / группа | Если → то | V × U | Обращение и конкретный метод | Владелец |
|---|---|---|---|---|
| T1 / технический | Если правила игнорируют усталость или конфликт сигналов, то предложенный объём может расти вопреки восстановлению | 4×5=20 | Снижаем: фиксированные приоритеты, валидация, синтетические RAT, внешняя экспертиза | Backend + специалист |
| T2 / технический | Если сохранение дневника тормозит на пике, то пользователь бросит ввод либо получит повторные запросы | 2×3=6 | Снижаем: путь без внешних API, 8.33 RPS модель, HTTP benchmark, bounded input, revision | Backend |
| A1 / архитектурный | Если обязательное решение зависит от LLM, то отказ, квота или недетерминированный ответ блокируют или меняют план | 3×4=12 | Избегаем зависимости: rule engine и шаблонные причины внутри процесса; LLM отсутствует | Технический лидер |
| B1 / бизнес | Если цикл не удобнее ChatGPT + заметок, то пользователи не выберут продукт | 4×5=20 | Снижаем: одинаковый сценарий в двух инструментах, порядок сбалансирован, 5–8 участников | UX |
| B2 / бизнес | Если дневник заполняется редко, то адаптации не хватает наблюдений | 3×4=12 | Снижаем: минимальная форма, сохранение без лишних полей, явный режим недостатка истории; 2-недельный пилот | Продукт |

## Архитектурная проверка перед изменениями

| Область | Решение и существенный риск | Верификация |
|---|---|---|
| Направление зависимостей | `internal/rhythm` не знает HTTP, cookies, Telegram или JSON-файлы | Review imports; domain unit tests |
| Интерфейсы | Port только у сохранения агрегата; интерфейс минимален и принадлежит потребителю | Review API/use-case и adapter |
| Composition root | `cmd/server` явно создаёт store, handlers, зависимости времени/секретов | Запуск с валидной и ошибочной конфигурацией |
| Lifecycle | Один HTTP-server; shutdown владеет ожиданием запросов; отдельные бесхозные goroutine не нужны | Shutdown test/ручная остановка; race |
| Конкурентность | Отменяемая блокировка и revision для общего store; один процесс на директорию | Конкурентная запись + stale revision + `-race` |
| Ошибки | Невалидные поля, конфликт, неавторизованный доступ и ошибка хранения различаются; UI не подтверждает неудачную запись | API negative tests и browser failure path |
| Атомарность | История и revision сохраняются вместе; nextPlan вычисляется из подтверждённого агрегата; ошибка записи не выдаётся за успех | Store failure/restart tests |
| Идемпотентность | Одна запись на запланированную сессию/день; тот же ID/содержимое повторяется без эффекта в пределах receipt-журнала; новая запись требует актуальную revision | Повтор одной отметки, два пропуска разных занятий |

## Проверки и критерий завершения текущего кода

Из корня репозитория:

```sh
gofmt -l cmd internal
go test ./...
go vet ./...
go test -race ./...
staticcheck ./...
go run ./cmd/rat
```

`staticcheck` выполняется при наличии бинарника. Его отсутствие фиксируется как «не запущен», а не «пройден». Для HTTP-теста отдельно запускается сервер и команда из матрицы. Go-код считается готовым к локальной демонстрации после успешных обязательных проверок, browser-прохода основной цепочки и сохранения фактического отчёта. Завершение кода не закрывает B1/B2 и не заменяет реальный запуск Telegram.

Заявка на высокий балл опирается на работающий цикл, эксперимент на этом цикле, сравнение исходной LLM-зависимости с детерминированным обходом и трассируемость. Оценку 10 определяет преподаватель; ни план, ни красивые экраны её не гарантируют.
