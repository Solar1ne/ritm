# Внутренний HTTP-контракт

API возвращает JSON с `Cache-Control: no-store`; исключение — скачивание календаря `text/calendar`. Ошибка имеет вид `{"error":{"code":"…","message":"…"}}`. Неизвестные поля JSON отклоняются. Изменяющие запросы требуют `Content-Type: application/json` и допустимые Origin/Fetch Metadata. Контекст отмены проходит в хранилище.

Клиент использует `state.today` как календарный день для обзора, форм и прогресса. Смена дня может происходить без смены `revision`, поэтому ответы помощника проверяются по обеим величинам. Подтверждение импорта передаёт `revision` просмотренного предпросмотра; при изменении данных или аккаунта требуется новый предпросмотр. Расчёт режима восстановления учитывает известную текущую неделю с заменами: [ADR-02](adr/002-deterministic-adaptation.md). Формат HTTP/JSON и версия экспорта не изменены.

## Идентичность, время и версии

`binding` — заголовок `X-Rhythm-Session` со значением `state.sessionBinding`. Это не самостоятельный токен авторизации: нужны корректная подписанная cookie и binding текущего аккаунта. Он обязателен на всех приватных маршрутах таблицы. Bootstrap `/api/state` без binding разрешён; присланный неправильный binding отклоняется. Публичные preview, health и первоначальная Telegram-авторизация его не требуют. `409 session_changed` требует нового входа: нельзя автоматически переслать старую форму под новым аккаунтом.

`identity` принимает `guest`, `account` или `telegram`; `accountsEnabled` показывает доступность постоянного веб-входа. Успешный GET `/api/state` продлевает только старую гостевую/Telegram-cookie на 30 дней. Новые управляемые сессии сайта и Telegram имеют абсолютный срок 30 дней от выдачи; GET его не продлевает. Cookie не переносится через резервную копию. Даты рассчитываются по часовому поясу сервера: по умолчанию `Europe/Moscow`; клиент получает `today`, `timeZone`, `currentWeekStart` и `historyEditableFrom`. Неделя начинается в понедельник.

## Постоянные аккаунты

| Метод / путь | JSON / доступ | Ответ |
|---|---|---|
| POST `/api/auth/register` | `{login,password,revision,keepGuestData:true}`; текущая гостевая cookie + binding | Состояние с `identity:account`, новый binding, cookie и однократный `recoveryCode` |
| POST `/api/auth/login` | `{login,password}`; без прежнего binding | Состояние существующего аккаунта и новая cookie |
| POST `/api/auth/recover` | `{login,recoveryCode,newPassword}` | `{recoveryCode}`; все прежние сеансы и код отозваны, нужен отдельный вход |
| POST `/api/auth/logout` | `{}`; действующая cookie требует binding | `{signedOut:true}`; отзыв текущей сессии и удаление cookies |
| DELETE `/api/account` | `{password, revision, confirmDelete:true}`; аккаунт Ритма, Origin и `X-Rhythm-Session` | `{accountDeleted:true}`; одна PostgreSQL-транзакция удаляет дневник, аккаунт и все его сеансы; cookies истекают |
| GET `/api/account` | Cookie постоянного веб-аккаунта + binding | `{login,createdAt,sessions:[{createdAt,expiresAt,current}]}` без токенов и session ID |
| POST `/api/auth/password` | `{password,newPassword}`; веб-аккаунт + binding | Состояние, новая cookie и `recoveryCode`; все старые сеансы отозваны |
| POST `/api/auth/recovery-code` | `{password}`; веб-аккаунт + binding | `{recoveryCode}`; предыдущий код недействителен |
| POST `/api/auth/logout-others` | `{}`; веб-аккаунт + binding | `{signedOutOthers:true}`; текущий сеанс сохраняется |

Тела ограничены 4 KiB. Все POST проходят те же проверки JSON/Origin/Fetch Metadata. Логин — 3–32 ASCII-буквы, цифры и `._-`, без различия регистра; это не email. Пароль — 15–128 Unicode-символов, до 512 байт, пробелы значимы. Слишком простой повтор одного символа отклоняется. Регистрация атомарно проверяет revision дневника и меняет владельца; старый гостевой доступ прекращается. Вход существующего пользователя не переносит текущий гостевой дневник.

Ошибки: `400 account_login/account_password/account_claim`; `401 credentials` без уточнения существования логина; `409 account_login_unavailable/account_conflict`; `429 auth_limit` с Retry-After; `503 accounts_unavailable/accounts_capacity/storage_unavailable`. Проверка старой cookie возвращает `401 session`; старый binding — `409 session_changed`. Клиент прекращает работу с устаревшей личностью. Неправильный пароль остаётся ошибкой формы, а не поводом повторять запрос автоматически.

Восстановление не входит автоматически в аккаунт. Новый резервный код возвращается только после изменяющей операции; в обычных state/export/info его нет. Экспорт не содержит логина, password hash, токенов или recovery digest. Удаление `/api/data` сохраняет credentials и сеансы. При потерянном ответе после регистрации или смены пароля нужно войти известным паролем и при необходимости выпустить новый код; повтор регистрации не создаёт дубликат. Повреждённое/отменённое чтение ledger даёт 503 без ложного подтверждения выхода. Некорректную или уже истёкшую cookie можно удалить через logout без binding, но действующая сессия требует правильной привязки.

До 10 действующих сеансов на пользователя; новый вход сверх лимита отзывает самый старый. Cookie содержит случайный токен и HMAC серверного секрета, а ledger — только хеш токена. Смена `SESSION_SECRET` отзывает доступ по старым cookie; повторный вход сохраняет владельца дневника. [Хранение, лимиты и конкурентность](adr/007-persistent-website-accounts.md).

## Ревизии и дневник

Каждое изменение принимает ожидаемую `revision`. Устаревшая версия даёт `409 revision_conflict`. Чтение атомарно материализует календарный переход или миграцию старого агрегата; только такой переход увеличивает revision. Повторные чтения той же недели её не меняют. После смены недели клиент перечитывает состояние перед изменением.

## Профиль, расписание и принятие предложения

Профиль: `{name,goal,experience,days,minutes}`. Цели `tone/strength/endurance`, опыт `beginner/regular`, дни 0–6 (понедельник — 0), от одного до пяти уникальных дней, длительность 15–90 минут, имя не длиннее 40 символов. `minutes` — базовая длительность занятия, не жёсткий лимит предложения следующей недели.

Состояние сохраняет прежние поля `revision,sessionBinding,identity,profile,entries,plan,nextPlan,decision` и добавляет `exportVersion,today,timeZone,currentWeekStart,historyEditableFrom,weeks,acceptedNextPlan,nextPlanToken,workouts,reminder,sessionAdjustments,hrvEntries,bodyEntries,mealSelections,ai`. Новые коллекции возвращаются массивами, в том числе пустыми.

`weeks` — неизменяемые снимки `{weekStart,source,profile,plan,acceptedToken?,acceptedAt?}`. `source` равен `baseline`, `accepted` или `legacy`. Внутри сохранённого снимка все статусы — `planned`; `/api/weeks` и текущий `plan` накладывают реальные статусы дневника. План содержит `{weekStart,sessions,totalMinutes}`; занятие — `{id,date,day,kind,title,minutes,status,detailsKnown}`. Изменение профиля не меняет текущую, прошедшую или уже принятую будущую неделю.

`nextPlan` — текущее предложение на следующую неделю. Оно рассчитывается от актуальных базовых настроек и текущих фактов, без накопления процентов. `acceptedNextPlan` — отдельно сохранённое расписание, которое пользователь уже принял. Для принятия передаются дата следующего понедельника и `nextPlanToken` именно показанного предложения. Несовпадение даёт `409 plan_conflict`. Точный повтор уже принятого token идемпотентен, в том числе при прежней revision. После новых отметок принятое расписание не меняется: до начала недели его можно отменить и принять новое предложение.

В понедельник принятое расписание становится текущим. Если пользователь ничего не принял, создаётся базовое расписание из профиля. Переход не создаёт выполненных или пропущенных занятий. Пропущенные календарные недели сохраняют расписания по известным базовым настройкам.

Старый дневник совместим с новым форматом. Для уже наблюдённых старых занятий, у которых не было снимка, `detailsKnown:false`, `minutes:0` означает **неизвестную** длительность, а не нулевую тренировку. Эти минуты не входят в сумму, текущий профиль не выдаётся за исторический. Для старой недели `profile` может быть null. Новые занятия имеют известные сохранённые параметры.

## Дневник и правила

Отметка: `{id,date,sessionId?,status,sleep?,fatigue?}`. ID — 1–80 ASCII-букв, цифр, `_` или `-`; дата — ISO, от `historyEditableFrom` (сегодня минус 90 дней) до сегодня включительно. `done/missed` требуют `sessionId` из сохранённого расписания этой даты; `wellbeing` — хотя бы один показатель. Сон — 0–24 часа, усталость — целое 1–10. Нельзя создать задним числом расписание, которого не было. Более ранние сохранённые факты доступны для просмотра, экспорта и явного удаления. Будущие синтетические записи текущей недели допустимы только в публичном preview.

Повтор того же ID с тем же payload идемпотентен даже при старой revision. Тот же ID с другим содержимым даёт `409 entry_conflict`. Исправление отправляется с новым ID: та же дата самочувствия или занятие заменяет существующий факт. В частичном исправлении отсутствующий/null показатель сохраняет предыдущее значение; это не команда удаления. Для полного удаления применяется DELETE. Сохранённая квитанция не позволяет старому повтору воскресить удалённую запись; чтобы заново внести факт, нужен новый ID.

Сон и усталость выбираются независимо: последняя известная величина каждого показателя по дате текущей недели, при одинаковой дате — последняя запись. Приоритет: восстановление при усталости ≥8 или сне <6; затем упрощение при двух пропусках; затем прогресс при выполненном плане и фактических сне ≥7 / усталости ≤4; иначе сохранение базового объёма. Чтение и preview не накапливают нагрузку.

## Импорт, резервная копия и ограничения

Импорт принимает содержимое файла в `content`, без URL или пути на диске. `format` — `csv` или `tcx`; сначала можно проверить состав и дубликаты. Импортированные тренировки хранятся отдельно от расписания. Зачёт занятия — отдельная явная опция `completePlanned`; он проверяется по сохранённому расписанию и окну редактирования. Повторный внешний ID не создаёт вторую тренировку. Удаление импортированной тренировки и удаление дневниковой отметки — отдельные действия.

Напоминание: `{enabled,time,beforeMinutes}`; время `HH:MM`, отступ 0/5/15/30/60 минут. Настройки используются клиентом и ICS. Сервер не рассылает сообщения Telegram. Календарь включает только занятия с известной длительностью. `/api/assistant` объясняет данные по правилам и возвращает `evidence` без внешних вызовов. Отдельные `/api/ai/*` описаны ниже.

Restore принимает экспорт версии 2 только в пустой аккаунт, включая отсутствие измерений и меню. Весь граф проверяется до единой записи: канонические типы/названия/длительности занятий, даты, суммы, ссылки и уникальность фактов, принятие будущей недели, тренировки, напоминание, серии измерений и ID рецептов. Восстанавливаются только пользовательские данные. `identity`, `sessionBinding`, исходная `revision` и квитанции операций не переносятся; версия назначения увеличивается на один. Это перенос данных, не восстановление чужой сессии и не слияние аккаунтов. Старые копии версии 2 без новых необязательных коллекций совместимы.

Обычное тело JSON ограничено 64 KiB, импорт — 2 MiB, восстановление — 5 MiB. Сохраняемый и читаемый агрегат ограничен одинаковыми 4 MiB; проверка размера выполняется до записи; PostgreSQL также проверяет размер канонического JSONB. На аккаунт допускаются по 500 фактов дневника, импортированных тренировок, HRV, состава тела и выбранных приёмов пищи, а также 520 недель. Новое превышение отклоняется, существующие пользовательские факты молча не удаляются. Каждый receipt-журнал ограничен последними 500 командами, поэтому гарантия повторов не бессрочна.

При недоступном хранилище сервер возвращает 503 без подтверждения записи. После COMMIT (или atomic rename в legacy file adapter), но до получения ответа результат может быть неопределённым: повторите тот же ID и payload либо выполните read-back. Ошибки валидации дают 400, отсутствующий объект — 404, превышение лимита агрегата — 413. Подробности интерфейсных сценариев и размещения находятся в [архитектуре](architecture.md) и [инструкции Telegram](telegram.md).

## Необязательный AI

`state.ai` и контекст содержат `configured`, `provider` (`DeepSeek` или `OpenAI`) и `model`. Контекстное согласие связано также с провайдером и моделью; их смена требует нового просмотра/подтверждения. [Конфигурация и живой smoke DeepSeek](deepseek.md).

Все endpoints требуют cookie и `X-Rhythm-Session`, POST также same-origin. `state.ai` сообщает `{configured,provider,model}`; ключ никогда не возвращается. Это конфигурация, не доказательство текущей доступности провайдера.

| Метод / путь | Вход | Результат |
|---|---|---|
| GET `/api/ai/context?task=ask\|review\|checkin` | Выбранная задача | `{status,revision,context,contextToken}`; факты для предварительного просмотра, допустимые даты, подпись со сроком5мин |
| POST `/api/ai/respond` | `{revision,task,message,consent:true,contextToken}` | `{mode:"ai",provider,model,revision,result,facts}`; ничего не записывает в дневник |

Текст ≤2000 Unicode-символов; review может не содержать текста. Сервер самостоятельно строит контекст: история за14дней, текущий/следующий план и выбранное меню ближайших7дней; имя и ID аккаунта не входят. Для checkin не передаётся история показателей. Контекст подписан с principal, задачей, revision, датой и сроком. Менять его на клиенте бессмысленно: сервер пересобирает данные. Смена данных/даты во время генерации отвергает результат.

Измерения ограничены последними шестью HRV и шестью записями состава тела внутри 14 дней; при усечении это явно указано. Названия приборов/условий и ID записей заменены локальными номерами сопоставимых серий. Неизвестные компоненты не заполняются из другой даты. Выбранное меню не объявляется фактом употребления или сведениями об аллергиях. Предпросмотр содержит ровно ту проекцию, которая отправится модели после согласия; изменение любой записи делает старое согласие недействительным.

`result`: `{title,summary,insights:[{text,factIds}],nextAction,draft}`. NextAction — только `journal|plan|activities|wellness|nutrition|none`, это подсказка навигации. Draft — null либо `{date,status,sessionId,sleep,fatigue}` для checkin. Неизвестные метрики остаются null. Сохранение требует отдельного `POST /api/entries` после проверки/правки пользователем; AI не получает прав на запись.

Ошибки: 400 `ai_consent`/`validation`;409 `conflict`/`ai_context_changed`;429 `ai_limit`;503 `ai_unavailable`. DeepSeek — 20 секунд, OpenAI — 3 секунды по умолчанию; `AI_TIMEOUT_SECONDS` задаёт 1–30 секунд, никакого автоматического retry; 4 параллельных вызова,6/аккаунт/10мин, по умолчанию60/процесс/час. Circuit:3 ошибки→60с паузы→пять успешных согласованных пользовательских probes. Ошибка/отказ/несовместимый ответ не становится ответом по правилам под маркировкой AI.

## Варианты занятий

| Метод / путь | Вход | Результат |
|---|---|---|
| POST `/api/sessions/variants` | `{revision,sessionId,constraints}` | Только preview: `{revision,original,current,adjustment?,options,recoveryRestricted,reasons}` |
| POST `/api/sessions/variant` | `{revision,sessionId,variantId,constraints}` | State с сохранённым вариантом |
| DELETE `/api/sessions/variant` | `{revision,sessionId}` | Возврат исходного занятия, если позволяют текущие ограничения восстановления |

Constraints: `{availableMinutes:15..originalMinutes,environment:"home|outdoors|gym",lowImpact:boolean}`. Каталог server-owned; тип и описание нельзя прислать произвольным текстом. Только сегодня/будущее в текущей или принятой следующей неделе, с известными деталями и без done/missed. Проверки восстановления ограничивают варианты. Повтор текущей сохранённой замены идемпотентен, прочие изменения требуют актуальную revision.

`state.sessionAdjustments` и export v2 содержат отдельный массив замен. Старые копии без поля совместимы; новый restore проверяет канонический каталог, даты, ссылки и лимиты. Исходные WeekSnapshot неизменны. Проекции занятия могут включать `variantId,environment,lowImpact,originalMinutes`. Следующее предложение не наследует локальные варианты; неделя с ними не подтверждает прохождение исходного объёма для автоматического +5%.

## HRV и состав тела

Все операции требуют cookie, binding и актуальную revision. Данные возвращаются через state/export.

| Метод / путь | Вход | Результат |
|---|---|---|
| POST `/api/hrv` | `{revision,entry:{id,date,valueMs,metric,window,source}}` | State с сохранённым измерением |
| DELETE `/api/hrv` | `{revision,id}` | State после удаления |
| POST `/api/body` | `{revision,entry:{id,date,weightKg?,bodyFatPercent?,method,source}}` | State с сохранённым измерением |
| DELETE `/api/body` | `{revision,id}` | State после удаления |

HRV: конечное `valueMs` в `(0,500]`; `metric` = `rmssd|sdnn`, `window` = `five_minutes|overnight|day`. Состав тела: хотя бы один компонент, вес 20–400 кг, процент жира `(0,75]`, метод `bia|dxa|skinfold|other`. Это границы допустимого ввода, а не клинические нормы. `source` — обязательное название прибора и условий до 60 Unicode-символов без управляющих знаков. Дата создания/исправления — сегодня минус 90 дней … сегодня; будущие измерения запрещены.

HRV-серия определяется metric/window/source, состав тела — method/source. Новый ID для той же даты и серии заменяет **всю** запись, отсутствующий компонент остаётся неизвестным. UI требует явного подтверждения такой замены. Тот же ID и payload — идемпотентный повтор, изменённый payload с тем же ID — конфликт. Receipts не позволяют старому повтору воскресить удалённую или заменить позднее исправленную запись в пределах своего горизонта. Удаление доступно и для более старой сохранённой истории; старые валидные записи переносятся через backup.

## Питание и меню

| Метод / путь | Вход | Результат |
|---|---|---|
| GET `/api/nutrition/catalog` | Cookie + binding | 18 рецептов, варианты фильтров, источники и ограничения подбора |
| POST `/api/nutrition/preview` | `{startDate,filters:{diet?,maxMinutes?,excludedAllergens?,meal?}}` + binding | `{selections,shoppingList}` без сохранения |
| POST `/api/meals` | `{revision,selection:{date,slot,recipeId}}` + binding | State после выбора/замены блюда |
| POST `/api/meals/batch` | `{revision,selections:[…]}` + binding | Атомарное сохранение 1–21 выбора |
| DELETE `/api/meals` | `{revision,date,slot}` + binding | State после удаления выбранного блюда |

В preview объект `filters` обязателен; пустой объект допускается. Недельный подбор использует все три приёма пищи, поэтому `meal` должен быть пустым. Начало — от сегодня до сегодня+8 дней включительно; результат покрывает семь дней. Отсутствие рецептов для выбранных ограничений даёт `422 no_recipes`, фильтры не ослабляются автоматически. Все видимые текущие фильтры отправляются и при немедленном нажатии подбора недели.

`slot` = `breakfast|lunch|dinner`; рецепт должен принадлежать каноническому каталогу и поддерживать выбранный слот. Изменение возможно от сегодня−90 до сегодня+14 дней; просмотр и удаление доступны для сохранённого архива. В batch нельзя повторять пару date/slot. Точный повтор текущего набора — no-op, устаревшее изменение — конфликт; частичного сохранения нет. Для удаления передаются дата и слот. Список покупок суммирует число повторов текстового количества ингредиента, не смешивая граммы и штуки. Меню — намерение, не дневник фактического питания.

`GET /api/health` сообщает фактический `storage` (`postgresql` или `file`). Недоступность PostgreSQL не переключает запросы на файловую копию. Инструкция и схема: [PostgreSQL](postgresql.md).

`state.limits` содержит серверные лимиты `entries`, `workouts`, `hrvEntries`, `bodyEntries`, `mealSelections`, `weeks`. Это производная метаинформация; restore не доверяет значениям из экспорта. Если календарное обновление упирается в лимит хранения, GET state/export и оба способа повторного входа повторно читают сохранённый агрегат: revision и snapshots не меняются, текущий план остаётся вычисленной проекцией. Мутации сверх лимита возвращают 413.

`DELETE /api/account` возвращает 400 при отсутствии явного подтверждения/revision либо неподдерживаемой guest/Telegram identity, 401 при неверном пароле/отозванном сеансе, 409 при изменившейся revision. Атомарное удаление требует PostgreSQL; файловый adapter возвращает 503 без изменений. После подтверждённого успеха клиент очищает приватный UI и открывает новый гостевой сеанс.
