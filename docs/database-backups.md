# PostgreSQL: резервные копии, очистка и проверка восстановления

Политика определяет, какие данные «Ритма» копируются, как долго хранятся копии и как оператор подтверждает восстановление. Ниже приведены команды для локального запуска и VPS.

<a id="backup-policy"></a>

## Политика резервного копирования

**Версия 1.0 от 14.11.2026.** Область действия — PostgreSQL 16 проекта «Ритм», включая рабочую БД `rhythm` и изолированные проверки восстановления.

| Параметр | Правило |
|---|---|
| Состав | Полный снимок прикладной БД в формате `pg_dump -Fc`. В него входят схема, индексы, дневники, аккаунты, сессии, ключ сессий из БД и история миграций. Конфигурацию развёртывания и внешние ключи хранит администратор отдельно. |
| Расписание | Ежедневно в 03:15 по часовому поясу VPS со случайной задержкой до 15 минут. `rhythm-backup.timer` догоняет пропущенный запуск после простоя. Перед изменением рабочей схемы создаётся отдельная проверенная копия. |
| RPO — допустимая потеря данных | Цель **24 ч 20 мин** при успешном ежедневном задании. Время учитывает интервал между копиями, разброс запуска и запас на создание. Для текущего объёма дневников суточной копии достаточно для выбранной цели. |
| RTO — срок восстановления | Цель **60 минут** от начала восстановления до проверки приложения. Полное время оценивают по восстановлению БД, настройке подключения и проверке входа, чтения и записи. |
| Хранение и очистка | На VPS используются `/var/backups/rhythm` и срок **7 суток**. Очистка сохраняет две последние проверенные копии, даже если они старше срока. Она удаляет только проверенные пары «архив и manifest» старше 7 суток и только при наличии свежей проверенной копии. Сначала строится список, затем `--apply` повторно проверяет его и удаляет кандидатов. |
| Независимое хранение | Предусмотрена зашифрованная копия на отдельном сервере или в объектном хранилище на **30 суток**. Доступ выдаётся отдельной учётной записи, загрузка подтверждается проверкой контрольной суммы. Назначение и автоматическую передачу ещё нужно подключить. |
| Доступ | Каталог на VPS имеет права `0700`, архивы и manifest — `0600`. Плановые копии создаёт сервис от `postgres`. Доступ к копиям получает назначенный оператор. |
| Контроль ошибок | Оператор проверяет статус и журнал systemd ежедневно. Если задание завершилось с ошибкой или последней проверенной копии больше **26 часов**, оператор выясняет причину и повторяет создание с проверкой. Внешние уведомления об этих событиях пока не подключены. |
| Проверка восстановления | Оператор восстанавливает доверенную копию в отдельную пустую БД минимум раз в неделю, перед первым релизом и после изменений схемы или процедуры копирования. В отчёте фиксирует архив, длительность и результат сверки известных записей и истории миграций. |
| Ответственность | Оператор следит за заданиями, выполняет контрольное восстановление и ведёт отчёт. Владелец проекта назначает оператора и принимает решение о переключении на восстановленную БД при аварии. |

Копия считается проверенной для хранения, когда совпали размер и SHA-256 из manifest и `pg_restore` прочитал архив целиком. Пригодность к восстановлению подтверждает отдельный запуск `restore-drill` с SQL-проверками. **Подтверждённый результат** — локальный прогон создания, восстановления и очистки от 14.11.2026. **На VPS** таймер был установлен при октябрьской выкладке. Установка новой версии скрипта и свежесть архивов на VPS этим прогоном не проверялись. [Результат квеста](evidence/quest-7-2026-11-14/result.json) · [Отчёт о VPS](vps-deployment.md).

`pg_dump` получает согласованный снимок одной БД при продолжающихся записях. Он не сохраняет cluster roles/tablespaces, конфигурацию PostgreSQL/сервиса, TLS, внешние API-ключи и файлы релиза. Их воспроизводимая конфигурация и секреты хранятся отдельно; внешний `SESSION_SECRET`, если задан, тоже нужен отдельно. В текущей модели импортированные тренировки входят в документ дневника, исходные пользовательские файлы не являются отдельным постоянным хранилищем. [PostgreSQL: SQL dump](https://www.postgresql.org/docs/16/backup-dump.html), [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html).

## Создание и проверка

Требуются Python 3 и PostgreSQL client tools. Для текущего PostgreSQL 16 используйте инструменты 16; другой major сначала проверьте отдельным drill. `RHYTHM_PG_BIN` задаёт каталог инструментов, иначе используется PATH и локальный Homebrew fallback. Подключение задаётся `DATABASE_URL` либо приватным `.local/database.env` (0600). Пароль не попадает в argv и вывод. Для native peer-аутентификации предусмотрен `--database rhythm` с обычными libpq-переменными.

```sh
backup_file=".local/backups/manual/rhythm-$(date -u +%Y%m%dT%H%M%SZ).dump"
python3 scripts/backup.py create "$backup_file"
python3 scripts/backup.py verify "$backup_file"
```

Старый вызов `python3 scripts/backup.py OUTPUT.dump` сохраняет смысл `create`. Существующие пути не перезаписываются. Один каталог защищён неблокирующим file lock: параллельное создание или очистка завершается с ошибкой, а не конкурирует с текущим заданием. Каждый вызов ограничен `--timeout 300` секунд, допустимо 1–3600.

Последовательность создания: `pg_dump --format=custom --no-owner --no-acl --no-password` → fsync → проверка custom header → `pg_restore --list` → полное декодирование в `/dev/null` → SHA256 → приватный manifest → публикация без перезаписи → fsync каталога. Незавершённые файлы при обычной ошибке убираются. При аварийном завершении возможен orphan без manifest; автоматическая очистка его не трогает.

`verified: true` означает совпадение размера/SHA256/имени с manifest и успешное чтение архива. **Это не доказательство выполнения SQL**: `pg_restore --list` проверяет TOC, а декодирование без `--dbname` выдаёт SQL без подключения. Восстановление и assertions проверяются отдельно. Manifest не переписывается после drill. [PostgreSQL: pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html).

Архивы и manifest содержат или позволяют получить частные данные: не добавлять их в Git/evidence/webroot. Проверка SHA256 обнаруживает повреждение, но не заменяет подпись и доверие к источнику. Восстанавливать можно только доверенный dump: SQL архива выполняется с правами восстанавливающей роли. Старые архивы без manifest сохраняются и не включаются в автоматическую ротацию; их проверяют вручную и создают новый штатный backup, не генерируют задним числом свидетельство успешной проверки.

## План очистки и применение

Сначала просмотрите JSON с `delete`, `keep`, `ignored`, `freshVerifiedCopy`. Dry run ничего не удаляет. Затем выполните ту же команду с `--apply`:

```sh
python3 scripts/backup.py prune .local/backups/manual --retention-days 7 --keep-last 2
python3 scripts/backup.py prune .local/backups/manual --retention-days 7 --keep-last 2 --apply
```

`--apply` заново проверяет файлы под тем же directory lock. Удаляются только пары `rhythm-YYYYMMDDTHHMMSSZ.dump` + `.dump.json`, которые прошли полную проверку, старше семи суток и не входят в две самые новые проверенные копии. Возраст определяется `mtime` архива. Если свежей проверенной копии в пределах retention нет, apply отказывает. Повреждённые, неизвестные, legacy-файлы и symlinks сохраняются в `ignored`, их разбирает оператор отдельно. Неполная пара после аварии удаления тоже сохраняется для ручного разбора.

Native wrapper сначала создаёт копию, при наличии hook завершает передачу off-host, печатает dry run и лишь затем применяет повторно проверенный план. Ошибка создания, проверки или hook останавливает wrapper **до очистки**. Это замена прежнему удалению всех файлов по одному условию возраста.

Для теста retention допустимо изменить `mtime` только собственных синтетических fixture-архивов через `os.utime`; содержимое и checksum остаются настоящими. Например, три успешно созданные копии с возрастом 10, 8 и 0 суток дают удаление только первой при `keep-last=2`. Manifest timestamp не используется для выбора. Интеграционный сценарий ниже явно записывает `backupAgesSimulated: true`, сначала проверяет неизменность файлов после dry run, затем реальное удаление старой пары и повторную проверку обеих оставшихся.

## Восстановление в отдельную тестовую БД

`restore-drill` требует отдельный `RHYTHM_RESTORE_DATABASE_URL` к maintenance database тестового PostgreSQL. Исходный `DATABASE_URL` автоматически не используется. Роли нужны права создания/удаления только тестовых БД; наилучший вариант — отдельный изолированный кластер без рабочих данных. Передавайте реквизиты через environment/secret, не литералом в историю команд.

```sh
python3 scripts/backup.py restore-drill "$backup_file" \
  --test-database rhythm_restore_test_manual \
  --assert-sql /private/path/known-records.sql
```

Helper допускает только имя `rhythm_restore_test_<lowercase_suffix>`, создаёт **новую** пустую БД из `template0`, выполняет `pg_restore --exit-on-error --single-transaction --no-owner --no-acl`, затем `psql --no-psqlrc --set=ON_ERROR_STOP=1 --file=...`. `--assert-sql` должен содержать настоящие assertions, например `DO ... RAISE EXCEPTION` при несовпадении известных записей; один `SELECT` без проверки не обнаруживает расхождение. Без assertions поле `assertionsPassed` равно `null`, а не `true`.

При успешном создании БД helper удаляет только её в `finally`, включая случай отказа restore/assertion. При существующей БД `createdb` завершается ошибкой, и helper её не удаляет. На очистку выделены дополнительные 30 секунд после основного timeout. Если cleanup не удался, exit ненулевой: оператор проверяет тестовый кластер и удаляет только созданную drill-БД после разбора. Успешный результат содержит `created`, `restored`, `assertionsPassed`, `cleaned`; все четыре должны быть `true` для drill с assertions. Восстановление одной транзакцией и создание пустой БД из `template0` соответствуют [инструкции PostgreSQL](https://www.postgresql.org/docs/16/app-pgrestore.html).

Для аварийного восстановления сервиса оператор сначала останавливает записи, сохраняет текущее состояние отдельной копией и проверяет выбранный backup в изолированной БД. Затем восстанавливает в новую целевую БД, отдельно предоставляет роли/права и secrets, сверяет migration ledger, известные записи, вход и чтение/запись дневника. Только после этого переключает конфигурацию приложения. Drill намеренно не переключает сервис и не содержит автоматического восстановления поверх рабочей БД. Зафиксируйте фактическую давность снимка, начало/конец восстановления и окно потерянных записей; не выдавайте целевые RPO/RTO за измеренные значения.

## Native timer, off-host и контроль

В release требуется `/opt/rhythm/current/deploy/backup.py` рядом с `backup.sh` и установленный `python3`. Сервис остаётся под `postgres`, с `UMask=0077`, доступом на запись только в `/var/backups/rhythm` и без сетевых AF_INET/AF_INET6 по умолчанию. `TimeoutStartSec=17min` покрывает создание и два прохода проверки retention по пять минут. Старые архивы без manifest не удаляются после обновления.

Дополнительная конфигурация читается systemd из необязательного `/etc/rhythm/backup.env` (root:root, 0600):

```ini
RHYTHM_BACKUP_RETENTION_DAYS=7
RHYTHM_BACKUP_KEEP_LAST=2
# После предоставления destination и установки проверенного hook:
# RHYTHM_BACKUP_OFFSITE_COMMAND=/usr/local/libexec/rhythm-backup-offsite
# RHYTHM_BACKUP_REQUIRE_OFFSITE=1
```

Hook — абсолютный путь к обычному исполняемому файлу, не symlink и без записи для группы/прочих. Он получает два аргумента: архив и manifest. Helper передаёт ему только базовое process environment и `RHYTHM_OFFSITE_*`; DATABASE_URL, PGPASSWORD, AI и Telegram credentials не передаются. У hook должны быть отдельные минимальные credentials. Он обязан шифрованно передать **оба файла**, проверить удалённый размер/checksum, обеспечивать 30-дневную политику на независимом хранилище и вернуть 0 только после подтверждения. `hook_succeeded` отражает exit code hook, не независимый аудит удалённого провайдера. При ошибке локальная проверенная копия сохраняется, задание завершается неуспешно, retention не запускается. `--require-offsite` без hook сразу отказывает.

Для сетевого hook оператор добавляет reviewed drop-in; единственного разрешения AF_UNIX недостаточно:

```ini
# /etc/systemd/system/rhythm-backup.service.d/offsite.conf
[Service]
RestrictAddressFamilies=
RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
```

Hook должен укладываться в общий пятиминутный бюджет `create`; для больших БД сначала измеряют dump/upload и согласуют новый бюджет и RPO. Путь credentials должен быть читаем сервисом с учётом `ProtectHome=yes` и не лежать в домашнем каталоге. Изменение каталога backup также требует согласовать `ReadWritePaths` и права, одной env-переменной недостаточно. Эти примеры не выполнялись на VPS.

После установки новой версии оператор проверяет:

```sh
systemctl daemon-reload
systemctl start rhythm-backup.service
systemctl show rhythm-backup.service -p Result -p ExecMainStatus
journalctl -u rhythm-backup.service --since '26 hours ago' --no-pager
systemctl list-timers rhythm-backup.timer
```

Оператор подключает внешний монитор к `Result/ExecMainStatus`, heartbeat успешного завершения и возрасту последней проверенной пары. Канал передаёт только имя сервиса, время и код ошибки, без DSN/дампа/PII. Проверка должна быть независимой от самого VPS, иначе его потеря скроет и сигнал. До предоставления канала владелец обязан явно считать это ручным контролем, а не настроенным alerting. При ошибке: сохранить последние копии, проверить место/права/доступность БД и клиентскую версию, исправить причину, повторить `create`, затем `verify` и drill. Не отключать проверки и не чистить каталог ради успешного статуса.

## Воспроизводимые проверки

Из корня проекта:

```sh
python3 -m unittest discover -s scripts -p 'test_backup.py' -v
python3 -m py_compile scripts/backup.py
sh -n deploy/native/backup.sh
python3 scripts/quest_7_check.py --evidence-dir /tmp/rhythm-quest7-run
```

Последняя команда требует PostgreSQL 16, Go и свободный loopback-порт 55442; каталог evidence должен быть новым. Она создаёт и останавливает собственный временный кластер, не использует рабочую БД, проверяет миграции и две известные синтетические записи, создаёт три настоящих custom dump, восстанавливает свежий в отдельную пустую БД с SQL assertions, выполняет dry run → apply и проверяет сохранённые копии. В evidence нет пользовательских записей или секретов. Кластер и архивы fixture удаляются при завершении; результат остаётся для проверки.

17 unit-тестов проверяют публикацию, права, блокировку, ошибки, целостность, ротацию и изоляцию восстановления. Локальный интеграционный прогон 14 ноября создал три архива PostgreSQL, восстановил два известных дневника в отдельную БД за 0,511 с и проверил очистку с сохранением двух пригодных копий.
