# ADR-04: Telegram как второй клиент с серверной проверкой личности

Дата: 17.10.2026. Статус: принято для кода; живое подключение зависит от внешней настройки. История: US12. Требование: NFR-08. Риск: утечка или подмена чужого дневника через доверие клиентскому ID.

## Решение

Один web-клиент и одно Go API обслуживают браузер и Telegram WebView. Telegram SDK используется только на границе клиента: состояние темы/окна и передача данных запуска. Домен планирования не импортирует Telegram-типы и не знает способ входа.

`POST /api/auth/telegram` принимает raw `initData`. Сервер проверяет HMAC по протоколу Telegram с bot token, сравнивает подпись constant-time и проверяет `auth_date`. В текущем контракте максимальный возраст — 1 час, допустимое время в будущем — 30 секунд. Положительный Telegram user ID становится principal только после проверки. `initDataUnsafe` и ID, присланный произвольно браузером, не считаются удостоверением личности.

Доверенная граница следует [официальной документации Telegram по валидации Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), проверенной 17.10.2026. Выбор 1 часа и 30 секунд — политика этого проекта, а не цитата требования Telegram.

Секрет `TELEGRAM_BOT_TOKEN` находится в environment сервера. Он не попадает в JS, export пользователя или логи. Сервер выдаёт сессию, а каждый запрос к данным проверяет principal. Гостевая история не объединяется с Telegram-историей автоматически: такое действие может переместить личные сведения между разными контекстами доступа.

При HTTPS подтверждённая Telegram-сессия использует HttpOnly cookie с `SameSite=None`, `Secure` и `Partitioned`; гостевая сохраняет SameSite=Lax. Перед выдачей Telegram cookie удаляется непартиционированный cookie того же имени. Сервер отвергает несколько одноимённых session cookie, чтобы не выбирать идентичность по случайному порядку.

State, auth и export возвращают `sessionBinding`, вычисленный HMAC от principal. `X-Rhythm-Session` обязателен для profile/entry/delete и export; state проверяет заголовок, когда он передан. Общий cookie может измениться в соседней вкладке, поэтому совпадающая revision сама по себе не разрешает запись. Несовпадающий binding даёт `409 session_changed` и блокирует операцию. Ошибка Telegram-входа не запускает молчаливый гостевой вход; черновики привязаны к той же идентичности.

## Альтернативы и последствия

| Вариант | Решение |
|---|---|
| Доверять `initDataUnsafe.user.id` / параметру URL | Отклонено: клиент может подставить чужой ID |
| Отдельное приложение и копия правил для Telegram | Отклонено: различие правил между каналами и удвоение тестов |
| Проверять подпись на клиенте | Отклонено: доверенный секрет нельзя передавать браузеру |
| Общий серверный auth adapter и единый domain | Принято: одна модель владения и один алгоритм для обоих клиентов |

Ограничение возраста уменьшает окно использования перехваченного initData, но не делает его одноразовым. Полная replay-защита требует отдельной серверной политики; нельзя приравнивать freshness check к одноразовому токену. Подпись также не доказывает успешную работу UI в конкретной версии Telegram.

## Что нужно для живого запуска

Нужны предоставленный командой token бота, размещённый HTTPS URL, секрет сессии и настройка Mini App в BotFather. Никакой фиктивный token не подтверждает этот этап. Локальный сайт и unit-tests можно выполнить независимо; сообщение «Mini App запущена» допускается только после открытия реальным Telegram-клиентом и проверки сохранения/повторного открытия.

## Проверка

Автотесты: валидный HMAC fixture; изменённая подпись/поля; отсутствующее и некорректное время; истёкшие и будущие данные; неверный user ID; отсутствие bot token; отделение guest и Telegram; пользователь A не получает профиль B. Команды: `go test ./...`, `go test -race ./...`.

[API tests](../../internal/httpapi/server_test.go) прошли, включая `TestTelegramAuthStableIsolatedAndNoGuestMerge`, `TestTelegramRejectsInvalidSignaturesAndDates`, `TestSessionBindingBlocksCrossTabIdentityChanges` и `TestAmbiguousSessionCookiesAreRejected`. [Браузерный отчёт](../evidence/browser.json) проверяет отказ/retry Telegram и смену общего cookie через SDK fixture. Это локальные автоматические проверки, не запуск настоящего бота и не проверка всех Telegram WebView.

Живой smoke после настройки: открыть Mini App → создать профиль → сохранить факт → закрыть → открыть снова → проверить ту же историю; открыть другим Telegram-пользователем → убедиться в изоляции. Эти шаги фиксируются отдельно от локальных fixtures и не считаются выполненными заранее.
