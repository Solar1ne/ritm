# ADR-03: атомарный JSON adapter для PoC, PostgreSQL для развития

Дата: 17.10.2026. Статус: историческое решение для первого PoC; заменено [ADR-08](008-postgresql-storage.md). PostgreSQL реализован и локально подключён 17.10.2026. Ниже сохранены основания прежнего решения. Риски: T2, целостность и владение данными. Требования: NFR-03/07; истории US01, US04–06, US11.

## Контекст

Презентация обосновывает PostgreSQL связанностью профиля, плана, дневника и версии решения. Для первого локального server PoC важно уже проверять реальную запись, перезапуск, изоляцию пользователей и конкуренцию. Внедрение DB-server не требуется для проверки самого правила адаптации, но отсутствие БД нельзя выдавать за успешный SQL load test.

## Решение для текущей сборки

`internal/filestore` хранит отдельный JSON-агрегат каждого principal. В версии 2 агрегат содержит профиль, неизменяемые снимки недель, diary entries, импортированные активности, настройки напоминаний, ограниченный журнал idempotency receipts и revision. Текущий `Plan` — сохранённое расписание с проекцией статусов; `NextPlan` — отдельное вычисляемое предложение. Принятие сохраняет его снимок в том же агрегате, а не в отдельном файле. Это исключает частичную запись «дневник новый, а сохранённый план старый».

Единая отменяемая блокировка сериализует операции в одном процессе. Ожидаемая revision проверяется в атомарной операции обновления. Повтор entry ID с тем же содержимым идемпотентен в пределах сохранённого журнала; тот же ID с другим содержимым — ошибка. Разные ID для одной тренировки корректируют её единственную отметку. Вызвавшая сторона получает копии mutable значений.

Перед заменой записывается временный файл с закрытыми правами, вызываются запись, file sync и close; затем rename и directory sync. Успех не кэшируется до завершения сохранения. JSON ограничен размером, история и receipt-журнал ограничены по числу. Имя файла выводится из проверенного principal, не из произвольного URL/пользовательского имени. Профиль и история не объединяются между principals.

## Сравнение

| Вариант | Почему принят / отклонён сейчас | Ограничение |
|---|---|---|
| **JSON aggregate + atomic replace** | Простая проверяемая запись без нового runtime; один профиль обновляется целиком | Один процесс, общий lock, перезапись всего агрегата, нет SQL/операционных DB-инструментов |
| **PostgreSQL — следующий adapter** | Транзакции, конкурентная запись нескольких процессов, миграции и relational queries | Требует размещения, схемы, резервного копирования и отдельного integration evidence |
| Только localStorage | Удобен для наброска интерфейса | Не проверяет серверное владение, restart и авторизацию Telegram; нет общего доверенного состояния |
| Векторная БД | Retrieval-задача в текущем продукте отсутствует | Не решает необходимость согласованной записи дневника |
| Отдельные файлы профиля, дневника и результата | Уменьшают отдельные записи | Вводят частично применённые изменения без общей transaction |

## Существенные ограничения

Один процесс на одну data-директорию — обязательный concurrency contract. Локальная блокировка не делает файловое хранилище multi-process-safe. 10 RPS smoke не подтверждает работу 10 000 одновременно активных пользователей и не сравнивает JSON с PostgreSQL.

После успешного rename и ошибки directory sync исход операции может быть неопределённым для клиента: новый файл уже может существовать. Клиент не должен автоматически создавать новую запись; повтор с тем же idempotency ID или перечитывание актуального состояния позволяет установить факт. Наличие sync не заменяет power-loss/backup/restore тесты.

Ограниченный receipt-журнал не является вечной гарантией идемпотентности. Перед многонедельным пилотом нужно согласовать retention, экспорт и удаление. Запуск в Telegram не переводит гостевую запись в аккаунт автоматически. Секрет подписания сессии сохраняется вместе с data и должен переживать перезапуск; его потеря нарушает доступность прежних гостевых сессий.

## Переход на PostgreSQL

Триггеры: нужны несколько серверных процессов; размер/частота записи упирается в lock/disk; продукт подтвердил пользу и нужны долгосрочная история, управляемые backup и SQL-аналитика. Миграция сохраняет principal, ID занятий, receipt/idempotency semantics и revision.

Use case задаёт атомарность «применить факт к текущему агрегату»; adapter реализует SQL transaction и проверку версии. Перед переключением: версия схемы, snapshot JSON, dry-run import, count/checksum и domain consistency checks, contract tests, rollback snapshot и повтор HTTP load. Без этих проверок target C4 не становится фактом внедрения.

## Проверка

`go test ./...`, `go test -race ./...`: перезапуск, concurrent updates, stale revision, идемпотентный retry, изменение возвращённой копии, ошибка записи, повреждённый JSON и недопустимый principal. `go run ./cmd/loadtest -url http://127.0.0.1:8080 -rps 10 -duration 30s` проверяет реальный HTTP + текущий adapter. Повтор с `-duration 5m` расширяет окно, но всё ещё не заменяет production-профилирование.

В финальном [локальном HTTP smoke](../evidence/http-load.json) выполнены 300/300 записей при 9.99934 RPS; p95 запроса 12.194417 мс; ошибок и drops нет. Setup/cleanup исключены из latency; все четыре искусственные guest-истории очищены через собственные сессии. Прогон шёл на фоне browser/race проверок. Это evidence текущего JSON adapter, а не PostgreSQL, нескольких серверных процессов или изолированной ёмкости оборудования.
