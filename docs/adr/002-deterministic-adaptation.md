# ADR-02: детерминированные правила вместо обязательного LLM-решения

Дата: 17.10.2026. Статус: принято. Связанные риски: T1, A1, B2. Требования: NFR-01/02/04; истории US04–06.

## Контекст и исходный риск

Продукт должен менять предложение по факту выполнения, сну и усталости и объяснять изменение. Если поручить обязательное решение внешней LLM, ответ зависит от её доступности, квоты и содержания генерации. Синтетические тесты должны обнаруживать конфликт «всё выполнено, но восстановление плохое». Обещание «ИИ подберёт безопасно» не является проверкой этого конфликта.

## Решение

Rule engine получает валидный профиль и дневник и возвращает план текущей недели, отдельное предложение на следующую неделю и шаблонные причины. Приоритет фиксирован: восстановление → упрощение → мягкий прогресс → сохранение. В исходном PoC LLM не подключалась. Расширение [ADR-05](005-optional-ai-and-session-variants.md) добавляет необязательные ответы и черновики, сохраняя основной расчёт независимым от модели.

Демонстрационные параметры:

| Условие | Действие |
|---|---|
| Усталость ≥8/10 либо сон <6 ч | Сокращение с учётом профиля и известной текущей недели; формула ниже, минимум 1 занятие по 15 минут |
| ≥2 разных пропущенных занятия, без признака восстановления | На одно занятие меньше; длительность сохранена |
| Все разные занятия выполнены; сон ≥7 ч; усталость ≤4/10 | Предложение +5% к базовой длительности вниз, максимум 90 минут |
| Истории нет или данные неполные | Нет прогресса; причина показывает отсутствие достаточных оснований |

Длительность в профиле задаёт базовое занятие, а не жёсткий лимит будущей рекомендации. Предложение не применяется автоматически и не умножает уже увеличенный план при каждом просмотре. Данные другой недели и повтор одной сессии не превращаются в новые достижения. Идентичность сессии и дедупликация остаются частью доменного контракта.

Уточнение от 22.10.2026: восстановление также ограничено сохранённой текущей неделей с выбранными заменами. Пусть `P` — число дней будущего профиля, `M` — минуты профиля, `K` — число текущих занятий с известной длительностью, `T` — сумма их минут. При `K > 0` число будущих занятий равно `min(max(1, P−1), max(1, K−1))`, минуты одного занятия — `min(max(15, floor(M×0.8)), max(15, floor(T×0.8/K)))`. Средняя округляется один раз после сокращения. Так текущие 3×15 дают 2×15, а текущие 1×15 при новом профиле 5×90 остаются 1×15. Минимум не позволяет гарантировать строгое уменьшение для 1×15.

При `K = 0` применяется профильное сокращение с явным объяснением невозможности сравнения с неизвестной текущей нагрузкой. Частично неизвестные длительности исключаются из числовой базы и обозначаются в причинах. Остальные режимы сохраняют профильную базу будущего предложения. Принятые сокращённые планы валидируются как канонические планы восстановления, поддерживаются экспортом/восстановлением v2 и переходом понедельника. Проверки: `TestRecovery*`, `TestFutureProfileRemainsBaselineOutsideRecovery` и HTTP-регрессия `TestHTTPRecoveryRespectsSavedWeekThroughAcceptanceAndRestore`.

Каждый показатель восстановления выбирается независимо по последней известной дате текущей недели. Запись одного сна не отменяет ранее известную усталость. При частичном исправлении отметки отсутствующее/null поле сохраняет прежнее известное значение; новое валидное значение заменяет его. Это предотвращает обход восстановления неполной записью. Контракт проверяют `TestIndependentSignalsCannotMaskRecovery` и `TestPartialCorrectionRemainsIdempotent`.

## Сравнение с исходным путём

| Критерий | LLM-only как исходная альтернатива | Принятый rule engine |
|---|---|---|
| Воспроизводимость | Требует отдельного контроля вариативности; одинаковые ответы не гарантируются выбором подхода | Для одинаковых валидных входов и недели одинаковый результат |
| Конфликт сигналов | Нужно отдельно оценивать и ограничивать результат генерации | Приоритет восстановления явно задан и проверяется |
| Отказ провайдера | Требуется внешний вызов, timeout и fallback | Внешнего вызова нет; ошибка провайдера отсутствует как причина отказа |
| Объяснение | Может быть выразительнее, но требует проверки соответствия фактическому решению | Причина привязана к сработавшей ветке и порогу |
| Стоимость/latency | Зависят от модели, объёма и тарифа; здесь не измерены | Только локальный расчёт; величина определяется новым RAT, не предположением |
| Возможности | Может обсуждать нестандартный контекст | Узкая поддержанная область; непредусмотренные ситуации не решаются генерацией |
| Безопасность для человека | Не доказана этим сравнением | Тоже не доказана; требуется экспертная проверка |

Оригинальный обход для защиты — убрать рискованную внешнюю зависимость из решения и сделать объяснение следствием проверяемой ветки. Это инженерное сравнение подходов, **не проведённый A/B benchmark LLM и не доказанное превосходство качества рекомендаций**. Для уровня 10 важно показать этот обход на рабочем образце и связать его с требованиями; окончательную оценку даёт преподаватель.

## Совместимость со старым PoC

В PDF упомянуты нормализация неизвестной цели и игнорирование ошибочного сна. Новый сервер отклоняет такие значения и не сохраняет запрос. Смена поведения намеренная: на внешней границе некорректный ввод не должен молча менять смысл данных. Результаты старых `node test.js` не считаются тестами этой версии.

## Проверка и ограничения

До нового прогона приняты критерии: 5/5 критических веток; ≥90% всех сценариев; 5 000 локальных вычислений, p95<50 мс. Команды: `go test ./...` и `go run ./cmd/rat`. Проверяются конфликты, отсутствие истории, границы, повторная отметка, повторный расчёт и связь текста причины с решением.

Результат нового Go-прогона 17.10.2026: [16/16, критические 5/5, 5 000 вызовов без ошибок, p95 0.01225 мс](../evidence/rat.json). Это текущая реализация, а не перенесённое число из старого Node.js PoC.

Технический RAT доказывает согласованность заданных правил на конечном наборе искусственных данных. Он не доказывает спортивную/медицинскую эффективность или достаточность порогов. Следующий этап — разбор специалистом, UX-тест и пилот. Любая будущая LLM остаётся вне принятия решения; её отказ не должен блокировать сохранение и шаблонную причину.
