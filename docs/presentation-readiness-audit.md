## 2. Авторизация и регистрация: точный ответ

При первоначальной проверке локального сервера до расширения аккаунтами получено:

```json
GET /api/health → 200
{"status":"ok","storage":"file","telegramConfigured":false}

GET /api/state → 200, только выбранные поля ответа:
{"identity":"guest","ai":{"configured":false,"provider":"OpenAI","model":"gpt-4.1-mini"}}
```

Cookie, идентификаторы сессии и содержимое дневника в отчёт не включены.

| Возможность | Статус |
|---|---|
| Гостевой доступ на сайте | Работает автоматически. Случайный идентификатор хранится в подписанной HttpOnly cookie; успешное чтение состояния продлевает сессию на 30 дней |
| Проверка доступа к данным | Есть: сервер определяет владельца по проверенной сессии; приватные операции требуют привязки к текущему аккаунту. Чужой ID из формы не даёт доступ к дневнику |
| Вход через Telegram Mini App | Реализован `POST /api/auth/telegram`: HMAC, проверка времени и пользователя, затем серверная сессия. Сейчас отключён без bot token |
| Регистрация в Mini App | Отдельный пароль не нужен: подтверждённый Telegram-пользователь получает устойчивую идентичность, затем заполняет профиль. Это ещё не проверено на настоящем боте |
| Регистрация / вход на сайте | Реализованы по логину и паролю; регистрация присоединяет гостевой дневник после подтверждения. Повторный вход работает в другом браузере |
| Восстановление веб-аккаунта | Однократный резервный код; смена пароля и выпуск нового кода. Старые сеансы отзываются |
| Email-вход, подтверждение почты и письма восстановления | Не реализованы; логин не является email |
| Вход через Telegram на обычном сайте | Отдельного сайта-входа через Telegram Login нет; запуск `/mini` вне Telegram не подтверждает пользователя |
| Выход и отзыв сессий | Выход отзывает текущую сессию; настройки показывают активные сеансы и позволяют завершить все остальные. Смена пароля отзывает все старые сеансы |
| Перенос гостевого дневника в Telegram | Только явный экспорт и восстановление в пустом профиле; автоматического объединения нет |

Гостевая сессия изолирует данные, но не заменяет восстанавливаемую учётную запись. Без регистрации очистка/потеря cookie лишает пользователя этого способа доступа; заранее скачанная копия позволяет восстановить данные в пустом профиле. После регистрации можно повторно войти по логину и паролю; резервный код позволяет сменить забытый пароль.

На HTTPS реализованы Secure cookies; для Telegram Web — SameSite=None и Partitioned, для гостя — SameSite=Lax. Возраст initData ограничен одним часом, допустимое будущее — 30 сек. Это ограничивает время повторного использования, но не делает initData одноразовым. Живую работу cookies в WebView ещё нужно проверить.

Основания: [auth.go](../internal/httpapi/auth.go), [маршруты веб-аккаунта](../internal/httpapi/accounts.go), [экран аккаунта](../web/static/account.js), [ADR-04](adr/004-telegram-client-and-identity.md) и [ADR-07](adr/007-persistent-website-accounts.md). Проверка нового входа: [Go/race/vet/staticcheck](evidence/accounts/verification.json), [два браузера и полный цикл](evidence/accounts/browser.json). Публичное размещение и настоящий Telegram требуют отдельных проверок.

## 3. Как обработаны пять рисков

Риски не объявляются устранёнными целиком. Оценки 20/12/6 — порядковые приоритеты из презентации, не вероятности и не результаты измерений.

| Риск | Механизм снижения / обхода | Доказательство | Что остаётся |
|---|---|---|---|
| **T1 · 20:** игнорирование усталости приводит к чрезмерному предложению | Фиксированный приоритет восстановления перед прогрессом; строгая валидация; неизвестные данные не становятся нулями; повторная отметка не удваивает выполнение; изменения принимаются явно | Go RAT: **16/16**, из них **5/5 критических**. Конфликт «всё сделано + усталость» даёт восстановление | Экспертная проверка порогов и пригодности для людей не проведена. RAT проверяет новые предложения; ранее принятый план сам не переписывается — его нужно явно отменить/принять заново |
| **T2 · 6:** медленный API мешает дневнику | Короткий путь без внешней модели, ограничение размера запросов, атомарная запись, версии состояния и обнаружение конфликтов | Локальный HTTP smoke: **300/300**, 30 с, около **10 RPS**, **p95 13.25 мс**, ошибок/пропусков 0. Есть tests restart, concurrent writes и отказа записи | Это один процесс Go/JSON на localhost. Нет подтверждения публичной ёмкости, SQL-профилирования, долговременной нагрузки и автоматической реакции на p95 за 5 мин |
| **A1 · 12:** отказ или непредсказуемость LLM ломает ответ/план | LLM исключена из обязательного расчёта. Локальные правила и причины доступны без ключа; AI не может самостоятельно записать дневник/изменить план. Deadline 3 с, после 3 ошибок пауза 60 с, затем 5 последовательных успешных пользовательских проб | Свежие tests: `TestAIDisabledDoesNotBlockDiaryOrRules` и `TestAIHTTPBreakerUsesOnlyAuthorizedRecoveryProbes` — PASS; весь базовый цикл работает без провайдера | Качество и реальная доступность генерации не проверены. Структурированный ответ не гарантирует истинность текста. Возврат использует согласованные запросы пользователей, а не фоновые платные health-check |
| **B1 · 20:** продукт не удобнее ChatGPT + заметок | Единый цикл, история, причины и действие без ручного копирования; подготовлен метод сравнительного UX-теста | Реализация сценария и план исследования есть; результата на людях **нет** | 5–8 участников, одинаковая задача в двух решениях; целевой выбор Ритма ≥60%. Стиль и число функций не доказывают превосходства |
| **B2 · 12:** редкие отметки оставляют адаптацию без данных | Короткий ввод, напоминания в имеющихся каналах, явный режим недостатка истории; нет автоматического прогресса без достаточных оснований | Тесты пустой/частичной истории и браузерный путь ввода | Двухнедельный пилот не проведён: цель ≥70% всех участников с ≥2 отметками в каждую неделю. AI-черновик пока не оценён на живой модели |

Дополнительные реализованные меры: изоляция владельцев, защита от смены аккаунта в соседней вкладке, проверка Origin/Fetch Metadata, отсутствие секретов/дневника в прикладных логах, ограниченные AI-квоты и контекст, отдельное согласие на передачу внешнему провайдеру. Они снижают конкретные риски, но не заменяют эксплуатационную проверку публичного сервера и управление сессиями.

## 5. Готовность к оценке и следующему запуску

По предоставленной шкале есть материалы для содержательной защиты высокого уровня: USM, MoSCoW/INVEST, сроки и зависимости, пять рисков с числами, C4, ADR, работающий образец и RAT на его правилах. Для пункта **10** нужно показать превышение планового уровня этапа и обоснованное сравнение альтернативы: обязательная LLM против локальных правил с необязательным помощником. Сравнение в ADR — инженерное, не проведённый эксперимент качества двух моделей. Оригинальность и итоговый балл оценивает преподаватель.

Рубрика не требует реализовать все Could-функции или закончить весь двухнедельный пилот, чтобы защищать RAT-PoC. Она требует связать риски, числовые требования, решения и проверки и честно показать результат наиболее рискованного допущения. Исследования B1/B2 и экспертиза остаются обязательствами дальнейшего продуктового плана, а не результатами этой сборки.

Приоритеты:

1. **Перед защитой:** синхронизировать PDF с фактической архитектурой и последними измерениями, приложить матрицу, проверить открываемую без входа ссылку и провести короткую демонстрацию конфликтного сценария. Соблюдение срока загрузки и присутствие команды по локальному коду не подтверждаются.
2. **Закрыто после аудита:** устойчивый веб-вход, восстановление резервным кодом и выход/отзыв сессий реализованы и проверены. Перед публичным запуском остаются HTTPS, внешний backup PostgreSQL с сохранением ключа, лимиты ingress и эксплуатационная проверка; почтовые функции не заявляются.
3. **Перед демонстрацией живых интеграций:** настроить серверный ключ модели, бот и HTTPS, проверить AI на искусственных данных и пройти настоящий Telegram-сценарий с двумя аккаунтами. Ключи не передавать в чат/клиент.
4. **Перед внешним пилотом:** экспертный разбор правил, эксплуатационные backup/restore, защита публичного ingress и контроль ресурсов, наблюдаемость, нагрузка на размещённом контуре. PostgreSQL уже подключён; production-размещение и распределённая нагрузка остаются отдельными проверками.
5. **Для подтверждения продуктовых рисков:** сравнительный UX-тест и двухнедельный пилот с заранее установленными критериями; не заменять их скриншотами или тестовыми пользователями.

## 6. Проверка этого аудита

Свежий узкий прогон: **7/7 тестовых функций PASS**, включая 11 отрицательных Telegram-вариантов и 5 проверок смены аккаунта между вкладками. [Вывод](evidence/presentation-audit/auth-ai-tests.txt) и [точная команда, дата и сверка хешей](evidence/presentation-audit/checks.json).

SHA-256 совпали для 58 записей Go/`go.mod` из AI-stage manifest и 82 записей Go/`go.mod`/`web/static` из premium-stage manifest. Ранее сохранённые результаты относятся к этим версиям: `go test -race`, `go vet`, `staticcheck`, сборка, 51 JavaScript-тест и 53 браузерные проверки/группы — PASS. AI и Telegram в браузерных отчётах проверялись имитациями. Полный suite и нагрузка в этом аудите заново не запускались.

Для воспроизведения инженерных проверок из корня проекта:

```sh
GOCACHE=/tmp/rhythm-go-cache go test ./...
GOCACHE=/tmp/rhythm-go-cache go vet ./...
GOCACHE=/tmp/rhythm-go-cache STATICCHECK_CACHE=/tmp/rhythm-staticcheck-cache staticcheck ./...
GOCACHE=/tmp/rhythm-go-cache go run ./cmd/rat -json
npm run check
npm test
```

Изменения этого запроса: документ аудита и его evidence. Прикладной код и API не менялись, новые тесты не добавлялись; повторены существующие проверки по вопросу о доступе и AI. Git-коммиты не создавались. Анализ выполнен по ECC production-audit; оценка готовности к запуску не подменяет учебную оценку 0–10.
